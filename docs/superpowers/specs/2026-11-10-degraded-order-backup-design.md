# 订单降级备份与正常恢复设计

## 1. 决策摘要

当正式订单因个别文件关系损坏而无法生成完整 Manifest 时，正常自动备份和普通失败重试继续采用严格校验，不得自动忽略异常。管理员只能从失败备份任务的订单明细中，针对 `RELATION_BROKEN` 订单显式创建独立的降级备份任务。

降级备份保存完整订单业务快照、所有当前能够可靠解析和下载的原始资产，以及无法解析的关系缺口。降级备份一旦成功，该订单即视为已经备份，后续不再进入自动备份候选，也不要求人工补偿或再次完整备份。

降级快照使用普通线上恢复入口。恢复只上传订单包中真实存在的资产，不为关系缺口伪造文件；全部可恢复资产提交成功后按正常恢复成功处理。订单及其快照始终展示“文件可能不完整”，无需额外恢复入口、风险确认或后续待办。

## 2. 背景与问题

当前正式订单 Manifest 解析采用失败关闭策略：任一有效业务关系引用的 `file_detail` 不存在、已逻辑删除或缺少必要对象元数据时，线上返回 HTTP 409 `RELATION_BROKEN`，本地将当前订单整体判为失败。

该策略能避免把不完整订单误记为完整备份，但存在永久漏备风险：只要线上脏关系未被修复，该订单的业务快照和仍然可用的其他文件也永远无法进入本地备份。普通失败重试不会改变数据状态，只会重复得到相同结果。

本设计在“不伪造完整性”和“尽可能保住已有数据”之间建立显式区分：严格备份仍代表完整；降级备份代表已完成但文件可能不完整。二者都是真实备份，不能与元数据模拟模式混淆。

## 3. 目标

- 保证单个文件关系错误不会永久阻断整个订单的业务快照和可用文件备份。
- 降级必须由管理员针对具体失败订单显式触发，不能成为自动备份的隐式兜底。
- 对缺失内容保留可验证证据，不能通过省略关系来制造“完整”假象。
- 降级备份成功后形成终态备份事实，不再自动重新备份该订单。
- 降级快照能够通过现有恢复入口恢复所有实际备份文件。
- 恢复不得伪造缺失文件、不得因关系缺口而要求上传不存在的 ZIP 条目。
- 保持订单级原子性：实际参与恢复的全部资产成功后才提交线上关系变更。

## 4. 非目标

- 不修复线上原有脏数据，也不生成缺失文件内容。
- 不重建已经不存在的线上订单主记录。
- 不为降级备份建立补偿待办、自动升级或定期重试机制。
- 不新增独立的降级恢复入口、恢复确认弹窗或恢复操作步骤。
- 当前不设计 COS 清理资格；但所有持久化证据必须保留完整性等级，禁止未来代码把降级凭证误认为完整凭证。
- 不改变本地补传文件规则，补传文件仍不参与线上恢复。

## 5. 领域模型

### 5.1 备份完整性

备份执行模式与备份完整性是两个正交维度：

- 执行模式：`REAL` 或 `METADATA_SIMULATION`。
- 完整性：`COMPLETE`、`INCOMPLETE` 或 `NOT_APPLICABLE`。

正式完整备份为 `REAL + COMPLETE`，降级备份为 `REAL + INCOMPLETE`，元数据模拟为 `METADATA_SIMULATION + NOT_APPLICABLE`。降级备份不能复用模拟模式，也不能仅依赖任务状态表达完整性。

### 5.2 降级快照

降级快照是管理员显式授权后形成的真实订单快照。它包含完整订单业务快照、全部成功备份的原始资产和零到多条关系缺口。降级快照是终态备份事实，不是待修复、待重试或处理中状态。

### 5.3 关系缺口

关系缺口表示备份时存在有效业务关系，但系统无法形成可下载原始资产。每条缺口至少固化：

- `relationKind`：关系类型；
- `sourceRecordId`：来源业务记录 ID；
- `relationOwnerKey`：只由关系类型和来源业务记录 ID 计算的稳定归属键，用于识别同一业务关系在文件缺失、修复或替换前后的身份；
- `originalFileId`：原文件 ID，可为空但必须保留缺失原因；
- `relationValue`：参与关系身份判断的稳定业务值；
- `reasonCode`：稳定原因码；
- `reason`：脱敏、限长的可读原因；
- `relationHash`：按稳定字段计算的关系身份摘要。

关系缺口不是资产，不能出现在恢复上传目标集合中。

### 5.4 规范摘要

降级 Manifest 使用版本化规范 JSON 计算摘要，初始版本为 `relationship-state-v1`：

1. 所有摘要字段在线上 JSON 中的 wire type 都是字符串或 `null`，禁止使用 JSON 数值。`null` 与空串严格区分，不得裁剪或互换。`sourceRecordId`、`originalFileId` 和 `assetIdentity` 是无符号十进制字符串，不含正号和前导零；`assetIdentity` 固定等于成功解析的 `file_detail.id`。`relationVersion` 取 `file_detail.updateTime`，其次取 `createTime`，按数据库原始本地时间格式化为固定九位小数的 `yyyy-MM-dd'T'HH:mm:ss.SSSSSSSSS`，不附加或换算时区；都不存在时固定为字符串 `"0"`。
2. `relationOwnerKey` 输入字段固定为 `relationKind/sourceRecordId`；`relationHash` 输入字段固定为 `relationKind/sourceRecordId/relationValue/originalFileId`。
3. 两种单条摘要都使用无歧义二进制编码：先写 ASCII 版本前缀（分别为 `relation-owner-v1`、`relation-v1`），再按固定字段顺序逐项写入 4 字节无符号大端 UTF-8 字节长度和字段字节；`null` 的长度固定为 `0xFFFFFFFF`。对完整字节流计算 SHA-256 小写十六进制。
4. 成功关系投影固定为 `assetIdentity/relationKind/sourceRecordId/relationOwnerKey/relationValue/originalFileId/relationVersion/relationHash`；关系缺口投影固定为 `relationKind/sourceRecordId/relationOwnerKey/relationValue/originalFileId/reasonCode/relationHash`，可读 `reason` 不参与摘要。
5. 成功关系按 `assetIdentity,relationKind,sourceRecordId,originalFileId,relationHash` 排序；缺口按 `relationKind,sourceRecordId,originalFileId,reasonCode,relationHash` 排序，比较值均为未转换的规范字段值，`null` 排在非 `null` 之前。
6. `relationGapHash` 是规范化后整个缺口投影数组的 UTF-8 JSON 字节 SHA-256；`relationshipStateHash` 是规范化对象 `{schemaVersion,resolvedRelations,relationGaps}` 的 UTF-8 JSON 字节 SHA-256。JSON 使用与现有 Manifest JCS 相同的属性排序、字符串转义和数值规范化实现；`schemaVersion` 固定为 `relationship-state-v1`。
7. `relationValue` 按关系类型取数据库字段原值，不做裁剪、大小写或路径归一化：`ORDER_FILE = fileCategory`、`DESIGN_PACKAGE = packageCode`、`DESIGN_PACKAGE_FILE = filePath`；`DESIGN_SCREENSHOT`、`DESIGN_MODEL`、`DESIGN_INSTRUCTION_TEMPLATE`、`DESIGN_INSTRUCTION_REVISED`、`DESIGN_DRAWING_TEMPLATE`、`DESIGN_DRAWING_QR`、`DESIGN_DRAWING_REVISED` 和 `FLOW_CARD` 固定为 `null`。增加关系类型时必须在新协议版本中显式定义其取值，不能沿用猜测值。
8. 冻结样例使用一个缺口关系 `ORDER_FILE/100/10.1/200` 和一个成功关系 `ORDER_FILE/101/10.2/201`：缺口 `relationHash = 7600c6ecaae9f218e11ad57ebde5435c0e1bfce319b4ad30713c3f66aeb0fbca`、`relationOwnerKey = 833b2616036ac177e7cd4acc107c35fad3e7d2cfc91b43f767e1adfc5fe94918`；成功关系 `relationHash = 3f3ea034c8a751c8539c6cfe4c97ca2792cc0364e0cddce232429d071e09b22a`、`relationOwnerKey = 55cd7a30b65df209c110650d9de99aebe1a0c89d5ca300e02a913036aae17ad6`。缺口原因为 `FILE_RECORD_NOT_FOUND`，成功关系 `assetIdentity = "201"`、`relationVersion = "2026-11-10T00:00:00.000000000"` 时，`relationGapHash = 9de5a02f7d3cff8ea6ad282b0d8530569ba5029f0bc15f931003dd3de3c8dac2`，`relationshipStateHash = ee8353533626fead52dfe9e0c5e7b6db8c35d7cf8bdd0b83bf32ef8bd518d11f`。

契约测试必须同时固化输入对象、排序后的规范 JSON 字节和上述摘要，线上与本地计算结果必须完全相同。摘要算法升级必须增加新版本，不得改变 `relationship-state-v1` 的历史结果。

## 6. 用户流程

### 6.1 正常备份

1. 自动任务或普通手工备份读取严格 Manifest。
2. 任一关系无法解析时，线上返回 `RELATION_BROKEN`。
3. 当前订单失败，任务继续处理其他订单并可进入 `PARTIAL_FAILED`。
4. 普通“重试失败订单”仍读取严格 Manifest，不得自动切换为降级模式。

### 6.2 创建降级备份

1. 管理员打开失败备份任务的订单明细。
2. 仅当订单终态失败码为 `RELATION_BROKEN`，且该订单此后尚无任何有效的完整或降级终态凭证时，显示“降级备份”。旧失败任务不能绕过后来形成的完整备份凭证再次发起降级备份。
3. 点击后创建独立任务，任务类型或配置快照必须明确标记 `DEGRADED_BACKUP`，不得修改或复用原失败任务。
4. 降级任务可以沿用单订单内针对网络、COS 或本地存储临时故障的重试机制，但不得重新进入严格 Manifest 流程。
5. 降级任务自身失败后，管理员仍可再次从同一失败订单发起降级备份；一旦成功，入口禁用或隐藏。

### 6.3 降级备份成功

1. 本地先把真实订单包和快照元数据持久化为不可见的 `STAGED` 制品，确保崩溃恢复后仍可继续发布。
2. 本地向线上原子提交带完整性等级的备份凭证；只有赢得订单终态凭证的任务可以继续。
3. 凭证成功后，本地把对应 `STAGED` 制品幂等发布为 `AVAILABLE` 快照；线上把该订单视为已经备份，候选查询不再返回该订单。
4. 本地订单列表和详情持续展示“文件可能不完整”。
5. 不创建后续任务、待办或自动完整性升级。

## 7. 线上降级 Manifest

### 7.1 独立接口语义

严格 Manifest 接口保持现状。降级任务调用显式的降级 Manifest 接口或显式解析模式；普通客户端无法因默认参数、超时或异常自动进入降级模式。

线上 Manifest 模块对每条业务关系独立解析：

- 能够可靠获得 `file_detail`、大小、对象定位和下载授权时，生成正常资产；
- 关系指向的文件记录不存在、已逻辑删除、缺少文件 ID、缺少必要对象元数据或 URL 关系无法匹配时，生成关系缺口并继续；
- 数据库不可用、权限失败、对象存储配置错误、无法签发本应可用资产的下载地址等系统性错误，必须使降级 Manifest 整体失败，不能伪装为关系缺口。

稳定的可降级原因码限定为：

| 原因码 | 条件 |
|---|---|
| `FILE_ID_MISSING` | 关系记录存在且可稳定识别，但文件 ID 为空 |
| `FILE_RECORD_NOT_FOUND` | 文件 ID 存在，但 `file_detail` 物理记录不存在 |
| `FILE_RECORD_DELETED` | `file_detail` 存在但已逻辑删除 |
| `FILE_SIZE_MISSING` | 文件记录存在，但大小为空或非法 |
| `OBJECT_KEY_MISSING` | 文件记录存在，但无法得到受支持的对象定位 |
| `ORIGINAL_FILENAME_MISSING` | 文件记录存在，但原始名称和存储名称均为空 |
| `URL_TARGET_NOT_FOUND` | 仅保存 URL 的业务关系无法匹配文件记录 |
| `URL_TARGET_AMBIGUOUS` | 同一 URL 匹配到多个有效文件记录，无法唯一确定资产 |

以下情况必须使降级 Manifest 整体失败：来源业务记录没有稳定主键、同一关系身份出现冲突字段、遇到未支持的关系类型或结构、数据库读取异常、签名/权限异常、预签名能力异常、对象存储配置异常，以及任何无法明确归入上述原因码的异常。非法对象定位若是单条文件元数据缺失，归入 `OBJECT_KEY_MISSING`；若反映平台配置或签发能力异常，则整体失败。

### 7.2 Manifest 根字段

降级 Manifest 在现有字段基础上增加：

- `backupCompleteness = INCOMPLETE`；
- `relationGaps`；
- `relationGapCount`；
- `relationGapHash`：规范化缺口集合摘要；
- `relationshipStateHash`：成功解析关系和关系缺口共同组成的关系状态摘要。

`manifestRevision/manifestJcsSha256` 必须覆盖订单业务快照、实际资产和关系缺口。现有 `relationSetHash` 可继续表示成功解析的资产关系集合，但恢复冲突判断必须使用覆盖缺口的 `relationshipStateHash`。

### 7.3 降级确认

文件下载完成后，降级备份仍需执行一致性确认。线上重新计算实际资产和关系缺口：

- 关系状态未变化时确认成功；
- 某缺口被修复、出现新缺口、关系转移或对象身份变化时返回 `MANIFEST_CHANGED`；
- 本地废弃本次临时制品并重新读取一次降级 Manifest，不能提交基于过期关系状态的降级快照。

## 8. 本地订单包与证据

### 8.1 订单包

订单包继续使用标准 ZIP 格式：

- `manifest.json` 保存完整降级 Manifest；
- 文件区只包含 `assets` 中实际下载并校验成功的文件；
- `relationGaps` 不创建占位文件或零字节伪文件；
- 当 `assets` 为空时，仍生成只含 Manifest 和必要订单元数据的有效订单包。

订单包的文件数量和源文件容量只统计实际资产；界面不得把关系缺口计入已备份文件数或用零字节表示。

### 8.2 本地持久化

订单快照增加独立完整性字段，例如 `backup_completeness`：

- 完整备份：`COMPLETE`；
- 降级备份：`INCOMPLETE`。

实际资产继续进入 `bk_asset`。关系缺口使用独立的结构化证据保存，优先建立 `bk_relation_gap`，并在订单包 Manifest 中保留同一不可变集合。至少保存快照 ID、关系身份字段、原因码、原因和关系摘要。

快照状态仍表示制品是否可用，不能用 `FAILED` 表示已成功形成的降级快照。任务成功、制品可用与内容完整性必须分别表达。

### 8.3 备份凭证与候选终态

线上凭证增加：

- `backupCompleteness`；
- `relationGapCount`；
- `relationGapHash`；
- `relationshipStateHash`。

完整和降级凭证都使候选进入“已备份”终态。候选查询、自动调度和普通失败重试不得再次选择已有有效降级凭证的订单。

凭证记录必须保留 `INCOMPLETE`，为未来 COS 清理等功能提供不可绕过的质量事实；本设计不定义其清理资格。

### 8.4 制品发布状态机

降级制品必须按 `STAGED -> RECEIPT_ACCEPTED -> AVAILABLE` 顺序推进，每一步均以订单 ID、Manifest 修订和任务幂等键绑定：

- `STAGED`：订单包已写入最终持久存储并完成哈希校验，快照元数据仅内部可见，不参与订单查询、下载或恢复；
- `RECEIPT_ACCEPTED`：线上终态凭证已原子接受，但本地快照尚未完成可见性切换；
- `AVAILABLE`：本地在同一事务中发布快照和订单投影，成为唯一可查询制品。

线上返回 `STATE_CONFLICT` 的竞争失败者必须把自己的 `STAGED` 制品标记为 `SUPERSEDED` 并按普通暂存清理规则处理，不能发布快照。若在凭证成功后、本地发布前崩溃，恢复任务必须先按原幂等键查询线上凭证：确认本任务是终态凭证持有者后，从持久化 `STAGED` 制品补做发布；未知结果不得清理制品或创建新快照。只有 `AVAILABLE` 可以对外称为已备份快照。

## 9. 界面与任务状态

### 9.1 失败任务

- 订单失败明细展示结构化失败码，不依赖解析中文错误信息判断是否可降级。
- `RELATION_BROKEN` 且尚无任何有效完整或降级终态凭证的订单显示“降级备份”。
- 原任务保持原终态；降级任务作为新的独立任务出现在任务中心。

### 9.2 订单文件

- 降级快照显示“文件可能不完整”标签。
- 详情显示实际备份文件数量、容量和缺失关系数量。
- 可在详情中展示关系缺口原因，但不生成待办或操作按钮。
- 下载订单包、冷备和普通查询仍按真实可用制品处理。

### 9.3 状态语义

- 降级备份的任务可以正常 `SUCCEEDED`。
- 降级快照的制品可以正常 `AVAILABLE`。
- 完整性单独为 `INCOMPLETE`，界面统一映射为“文件可能不完整”。

任何界面不得把 `SUCCEEDED/AVAILABLE` 翻译为“文件完整”。

## 10. 正常恢复语义

### 10.1 统一入口

完整快照和降级快照使用同一恢复入口、同一任务类型和同一上传流程。选择降级快照时不新增确认弹窗或风险提示；订单已有的“文件可能不完整”标签承担信息展示职责。

### 10.2 本地恢复清单

- `assets` 是恢复计划的完整上传目标集合；
- `relationGaps` 是只读证据，不进入上传目标集合；
- 本地包检查只要求每个 `assets` 条目均存在并通过哈希、大小校验；
- 不检查关系缺口对应的 ZIP 条目，因为它们从未被备份；
- `assets` 为空时不创建线上恢复会话，订单结果使用现有 `SKIPPED` 状态并记录“无文件可恢复，已跳过”，不算恢复失败；若任务内没有其他失败订单，恢复任务整体仍为 `SUCCEEDED`。

### 10.3 线上恢复预检

现有默认 `REJECT` 策略不能继续调用失败关闭的严格 Manifest，否则降级快照永远无法恢复。恢复模块必须使用可返回关系缺口的关系状态检查：

- 当前 `relationshipStateHash` 与降级快照一致时，允许按普通恢复继续；
- 缺口被修复、关系新增/删除、关系转移或当前文件身份变化时，视为线上状态已变化，按现有冲突策略处理；
- `relationOwnerKey` 用于识别同一来源业务关系：缺口后来绑定了新的线上文件时视为“缺口已修复”，不能因为新文件 ID 导致 `relationHash` 改变而误判为另一条可覆盖关系；
- 不能仅因为存在关系缺口就自动切换到 `FORCE_OVERWRITE`；
- 即使使用覆盖策略，也必须验证请求资产和关系缺口来自受信任、摘要校验通过且订单 ID 一致的备份 Manifest，不能允许任意文件 ID 绑定到目标订单。

冲突策略的具体边界为：

- `REJECT`：当前 Manifest 修订和 `relationshipStateHash` 都必须与备份一致。
- `CONFIRM_OVERWRITE/FORCE_OVERWRITE`：允许仍属于同一订单、同一 `relationOwnerKey` 的实际资产内容或对象定位发生变化；允许原关系缺口已经修复，并保持修复后的新文件及其关系不变；允许出现新的线上关系，并保持新关系不变。
- 任意策略都不允许恢复包重建已经删除的业务关系、接管已转移到其他订单的关系、改变关系类型或来源记录，或为关系缺口创建文件。出现这些情况时整单返回 `RESTORE_CONFLICT`。

覆盖策略只决定是否可以回写备份中真实存在且仍归属目标订单的资产，不授予重写关系结构的权限。

关系状态转换按下表处理：

| 备份状态 | 当前线上状态 | `REJECT` | `CONFIRM_OVERWRITE/FORCE_OVERWRITE` |
|---|---|---|---|
| 已解析文件 A | 同一 `relationOwnerKey`、同一文件 ID A | 状态摘要一致才允许 | 可恢复 A 的内容或对象定位 |
| 已解析文件 A | 同一 `relationOwnerKey`、不同文件 ID B | 冲突 | 冲突；不得覆盖 B、不得把 A 重新绑定到该关系 |
| 已解析文件 A | 同一 `relationOwnerKey`，当前文件记录 A 缺失或已逻辑删除 | 冲突 | 仅当当前关系仍明确引用 A 时，可用备份资产重建或恢复 `file_detail(A)`；当前文件 ID 为空或不同则冲突 |
| 关系缺口 | 同一 `relationOwnerKey`，缺口已修复为文件 B | 冲突 | 保留 B，不上传或回绑任何缺口资产 |
| 关系缺口 | 同一 `relationOwnerKey`，仍为缺口 | 状态摘要一致才允许 | 保持当前缺口，不创建文件 |
| 任意 | 关系已删除、转移订单、改变类型或来源记录 | 冲突 | 冲突 |
| 备份中不存在 | 当前新增关系 | 冲突 | 保留新增关系，不由恢复事务修改 |

因此，“缺口已修复”只适用于备份时本来没有资产的关系；“已解析文件后来缺失”属于真实备份资产的恢复场景，只有仍引用同一文件 ID 时覆盖策略才可恢复该文件。两者不得混用。

### 10.4 上传与提交

1. 线上只为实际资产生成上传目标。
2. 本地要求所有计划资产上传成功，集合必须完全一致。
3. 线上提交前重新计算当前关系状态并校验计划摘要及冲突策略。
4. 在单个事务中只更新本次实际恢复资产对应的 `file_detail` 和必要冗余 URL。
5. 关系缺口保持原状，不插入空 `file_detail`，不清空业务关系，也不生成虚假对象。
6. 全部实际资产提交成功后，恢复订单按正常成功处理；快照完整性和“文件可能不完整”标签不变。

恢复不会重建订单主记录。线上订单不存在或已逻辑删除时仍按现有规则跳过。

## 11. 失败与并发场景

- 降级 Manifest 读取期间关系变化：确认阶段返回 `MANIFEST_CHANGED`，重新读取后再备份。
- 降级备份期间可用资产下载失败：当前订单失败，不得把下载失败追加为关系缺口。
- 降级凭证提交结果未知：沿用幂等查询，不重复生成第二个快照。
- 同一订单并发发起多个降级任务，或完整与降级备份并发：线上按订单原子提交首个有效终态凭证，`COMPLETE/INCOMPLETE` 共用唯一终态约束；后到提交返回 `STATE_CONFLICT`。失败竞争者不得发布本地快照，已产生的暂存制品按普通失败清理规则处理并保留任务审计。
- 恢复准备后缺口被修复或关系变化：提交阶段返回冲突，不能覆盖新状态。
- 恢复包缺少一个实际资产：整单恢复失败并终止会话。
- 恢复包仅含关系缺口：本地跳过，不调用线上准备接口。
- 已有降级凭证后自动任务再次扫描：候选接口不返回该订单。

## 12. 兼容性与迁移

- 新生成的 Manifest 显式写入 `manifestSchemaVersion = 2`；`relationshipStateHash`、`relationGaps` 和 `relationOwnerKey` 只在 v2 语义下参与校验。
- 历史 `REAL` 正式快照在迁移时回填 `backup_completeness = COMPLETE`。
- 历史 `METADATA_SIMULATION` 快照回填 `backup_completeness = NOT_APPLICABLE`，字段使用非空三值枚举，不用 `null` 表示未知。
- 历史 v1 Manifest 没有 `relationGaps` 时按空集合处理，但只有 `REAL` 正式快照才能推断为 `COMPLETE`；不得根据不完整的历史证据补造 v2 `relationshipStateHash`。
- 新版线上服务继续接受历史 v1 Manifest，并沿用原 `manifestRevision/relationSetHash` 恢复校验逻辑；只有 v2 Manifest 才使用 `relationshipStateHash` 和本设计的缺口冲突规则。
- 现有严格 Manifest、正常备份和正常恢复协议保持兼容。v2 新字段均为 JSON 增量字段；旧本地服务可继续使用 v1 严格协议，但没有能力调用降级 Manifest 接口或提交降级凭证。
- 降级接口和凭证提交必须显式协商协议能力；任一端不支持 v2 时返回明确的版本不兼容错误，禁止回退成无缺口证据的“完整”快照。
- 任务失败记录需要保留线上结构化 `code`，以可靠识别 `RELATION_BROKEN`。

## 13. 安全与不变量

- 自动备份永不自动降级。
- 普通失败重试永不自动降级。
- 只有明确的管理员操作可以创建降级任务。
- 降级只容忍业务关系/文件元数据缺口，不容忍下载、哈希、存储或认证失败。
- 关系缺口必须进入 Manifest 修订和恢复冲突摘要。
- 缺失文件永不使用零字节占位符冒充真实资产。
- 恢复只提交实际上传并验证成功的完整资产集合。
- 降级凭证可以终结备份候选，但永远保留 `INCOMPLETE` 质量事实。

## 14. 验收场景

1. 正常自动备份遇到一个缺失 `file_detail` 时，订单失败且不会自动生成降级快照。
2. 普通“重试失败订单”仍失败关闭，不会进入降级模式。
3. 管理员对 `RELATION_BROKEN` 订单点击“降级备份”，系统创建独立任务。
4. 一个关系缺失、两个文件正常时，订单包包含两个真实文件和一条关系缺口，任务成功。
5. 所有关系均无法解析时，生成只含 Manifest 的有效订单包，任务成功。
6. 下载、哈希或热备存储失败时，降级任务失败，错误不能转成关系缺口。
7. 降级凭证生效后，候选查询不再返回该订单。
8. 订单列表、详情和下载视图持续显示“文件可能不完整”。
9. 恢复包含实际资产的降级快照时，使用普通入口，无额外确认，全部实际资产上传并提交后任务成功。
10. 恢复零资产降级快照时，显示“无文件可恢复，已跳过”，不创建线上会话。
11. 恢复不得为关系缺口创建空文件记录，缺口关系保持不变。
12. 备份后线上缺口被修复或关系发生变化时，默认恢复策略检测到冲突并拒绝静默覆盖。
13. 完整快照的备份与恢复行为不受降级功能影响。
14. 线上与本地针对冻结规范样例计算出完全一致的 `relationshipStateHash`。
15. 同一订单的完整与降级备份并发提交时只有首个终态凭证生效，失败竞争者不发布本地快照。
16. 覆盖恢复遇到关系删除、转移或关系类型变化时整单拒绝；遇到缺口已修复或新增关系时保留线上新状态。
17. 历史 v1 完整快照继续按原协议恢复，不要求存在 `relationshipStateHash`，也不会被错误推断为 v2 降级快照。
18. 零资产降级快照恢复时订单结果为 `SKIPPED`；任务内没有其他失败订单时任务整体为 `SUCCEEDED`。
19. 旧失败任务在订单后来已有完整或降级终态凭证后不再显示“降级备份”，服务端重复发起同样返回 `STATE_CONFLICT`。
20. 线上凭证接受后、本地发布前进程崩溃时，重启后使用原幂等键确认凭证并把原 `STAGED` 制品发布为唯一 `AVAILABLE` 快照。
21. 备份关系指向文件 A、线上同一关系后来改指文件 B 时，所有策略均拒绝用 A 覆盖或重新绑定 B。
22. 备份关系指向文件 A、线上关系仍引用 A 但 `file_detail(A)` 后来缺失时，默认策略冲突，覆盖策略可从真实备份资产恢复 A。

## 15. 实施边界

该设计需要同时修改：

- 线上 Manifest 解析、确认、备份凭证、候选判断和恢复关系状态校验；
- 本地远端错误结构、本地任务类型、降级任务创建、订单包生成、快照/关系缺口证据和恢复清单读取；
- 本地数据库迁移、接口契约和前端任务/订单展示；
- 线上与本地的单元测试、契约测试、集成测试及恢复原子性测试。

实施计划必须按契约和数据模型先行、线上能力、本地备份、本地展示、恢复适配、端到端验证的顺序拆分，避免在协议尚未稳定时先增加前端入口。
