# 本地备份系统：动态存储卷管理设计

## 1. 目的与结论

本设计将本地备份系统现有的“单一热备根目录 + 相对存储键”模式，升级为“**存储卷台账 + 文件副本归属卷 + 动态路由**”模式。

目标是让本地磁盘、NAS 共享目录、可移动冷备硬盘统一作为可管理的存储卷。系统可以在 A、B、C 多个热备卷之间切换新写入目标，同时不影响历史订单包的读取、下载、冷备处理和线上恢复；已离线的冷备盘重新接入后，可直接读取其中订单包并恢复线上，无需先复制回热备区。

本设计不要求在开发阶段直接接入 NAS。Windows 本地目录、多块本地盘或 USB 存储盘可完整模拟多卷、切换、离线与重新接入流程。客户现场 NAS 只要以 Windows 服务账号可访问的目录形式提供，即可走同一条访问链路。

## 2. 已确认的业务规则

1. 一个订单 ZIP 包及补传文件必须记录其**所属存储卷**和相对路径，不能只保存相对路径。
2. 系统同一时刻仅允许一个 `HOT + ACTIVE` 存储卷作为自动订单备份的写入目标。
3. A 卷容量不足时，可以切换 B 为 `HOT + ACTIVE`；A 自动成为 `HOT + READ_ONLY`，其中历史数据保持可读。
4. 可配置容量阈值和备用热备卷优先级。阈值触发时，系统可自动切换到已纳管、在线、健康且容量足够的备用热备卷；不能自动选择未纳管的新插入介质。
5. 冷备盘 A 离线后，对应订单包状态为冷备存在、卷状态为 `OFFLINE`。重新插入并完成识别后，卷成为 `COLD + ONLINE`，可直接下载或发起线上恢复。
6. `COLD + ONLINE` 可直接读取，但不会被自动备份作为写入目标，也不纳入当前热备可写容量。
7. 管理员可将已接入的冷备卷主动转换为 `HOT + READ_ONLY` 或 `HOT + ACTIVE`；转换前必须完成目录、容量、健康和任务互斥校验。
8. “冷备导入区”只保留给不能直接挂载原冷备卷的兼容场景，例如仅拿到一个冷备批次大压缩包并复制到服务器后进行导入。

## 3. 术语与状态模型

### 3.1 存储卷

存储卷是一个已被系统纳管、且服务账号可访问的目录根。它可以是 Windows 本地固定盘目录、可移动盘目录、NAS UNC 共享目录，或系统级挂载的网络目录。

存储卷不是 Windows 盘符本身。例如 `E:\yigongbao-cold-a`、`\\nas01\backup\hot-b` 分别是两个可独立管理的卷根目录。

### 3.2 三个独立状态维度

| 维度 | 可选值 | 含义 |
|---|---|---|
| 存储层级 `tier` | `HOT`、`COLD`、`IMPORT` | 热备、冷备、兼容导入区 |
| 挂载状态 `mount_status` | `ONLINE`、`OFFLINE`、`UNAVAILABLE`、`UNKNOWN` | 是否可访问及最近探测结果 |
| 写入状态 `write_status` | `ACTIVE`、`STANDBY`、`READ_ONLY`、`DISABLED` | 是否允许作为自动写入或人工写入目标 |

`COLD + ONLINE + READ_ONLY` 是“冷备盘重新插入、可直接恢复”的标准状态。它不是热备盘。

### 3.3 文件副本定位

每一个订单包、补传文件、冷备副本均须以以下组合唯一定位：

```text
storage_volume_id + storage_key
```

其中 `storage_key` 是相对路径，例如：

```text
orders/2026-11-06/20260707000021-31.zip
supplements/20260707000021/design-file.zip
```

系统运行时由存储卷根目录与相对键拼接真实路径。历史文件永远依据其记录的卷读取，切换当前热备卷不会改变历史包位置。

## 4. 存储卷发现、纳管与识别

### 4.1 自动发现范围

第一期仅发现 Windows 服务账号当前可见、可访问的目录：

- 本地固定磁盘；
- 可移动磁盘、USB 硬盘；
- 已系统级挂载的网络驱动器；
- 管理员预先提供且服务账号可访问的 UNC 共享目录。

系统必须区分“发现到候选路径”与“已纳管存储卷”。发现不等于允许读写；管理员确认纳管后才创建存储卷记录。

### 4.2 NAS 边界

系统不在第一期保存或管理 NAS 账号密码，也不承诺无凭据枚举局域网全部 NAS 及共享目录。客户环境应由运维将 NAS 共享以 UNC 路径或系统级挂载方式提供给备份服务账号。

推荐使用 UNC 路径，如 `\\nas-host\backup-share\hot-a`。不推荐依赖某个交互式 Windows 用户映射的 `Z:` 盘，因为 Windows 服务通常不可见该映射。

### 4.3 卷身份校验

候选卷纳管时，系统记录：

- 路径与访问类型：`LOCAL_PATH`、`UNC_SHARE`，预留 `NAS_API`；
- 容量域身份、卷 GUID / UNC 共享身份等可获取指纹；
- 系统写入的卷标记文件（例如 `.yigongbao-volume.json`），包含随机卷 UUID、创建时间与不可变校验信息；
- 总容量、可用容量、文件系统、最近探测时间及延迟。

冷备盘重新插入时，系统通过卷指纹和标记文件匹配既有卷记录，不以易变化的盘符作为唯一身份。识别失败、标记缺失、卷 UUID 冲突或目录不匹配时，不自动纳管为原卷，必须提示管理员处理。

## 5. 热备写入与扩容流程

### 5.1 手动切换（基础且必须提供）

1. 管理员在存储卷管理页发现并纳管 B 卷。
2. 系统探测 B 的读写、容量、可达性和卷标记完整性。
3. 管理员将 B 设置为 `HOT + ACTIVE`。
4. 系统检查不存在正在执行的订单备份任务；通过后，以事务方式将旧 ACTIVE 卷 A 改为 `HOT + READ_ONLY`，B 改为 `HOT + ACTIVE`。
5. 后续新备份任务在创建时固化目标 `storage_volume_id=B`；该任务即使执行中发生默认卷切换，也不得改变写入位置。
6. A 上已存在的历史订单包仍按 A 定位，可下载、恢复或转入冷备。

### 5.2 自动切换（在基础能力完成后启用）

自动切换不是“发现新盘后立即使用”，而是从已纳管的 `HOT + STANDBY` 卷中选择。触发条件为当前 ACTIVE 卷的可用容量低于阈值，或连续健康检查失败。

候选备用卷必须同时满足：`ONLINE`、健康检查通过、可写、剩余容量满足“预计包大小 + 安全保留量”、优先级最高。

如果没有符合条件的备用卷，系统不得写入未知盘或冷备盘；应暂停后续备份任务、持久化告警并通知管理员。已运行任务保持使用其创建时锁定的卷；若该卷不可写，按该订单失败策略处理。

### 5.3 A → B → C 示例

| 时间 | A | B | C | 新订单写入位置 |
|---|---|---|---|---|
| 初始 | `HOT + ACTIVE` | 未纳管 | 未纳管 | A |
| A 将满 | `HOT + READ_ONLY` | `HOT + ACTIVE` | `HOT + STANDBY` | B |
| B 将满 | `HOT + READ_ONLY` | `HOT + READ_ONLY` | `HOT + ACTIVE` | C |
| A 转冷备并拔出 | `COLD + OFFLINE` | `HOT + READ_ONLY` | `HOT + ACTIVE` | C |

## 6. 冷备、离线与直接恢复流程

### 6.1 热备转冷备

冷备任务完成并校验通过后，管理员确认删除源热备文件。系统需要保留冷备副本与其所属卷关系，并将订单包的热备副本标记为不存在；不删除订单快照、文件清单、校验值和冷备卷关联记录。

若 A 盘整体作为离线冷备介质，管理员将 A 标记为 `COLD + OFFLINE + READ_ONLY` 后再物理拔出。不能因为拔出导致订单记录或文件副本记录被删除。

### 6.2 冷备卷重新接入后直接恢复

1. 运维插入 A 盘或重新挂载其 NAS / 网络路径。
2. 系统扫描到候选卷，并通过指纹与卷标记匹配 A 的既有记录。
3. 管理员执行“确认挂载”；系统探测目录、抽样校验或按需校验目标 ZIP。
4. A 更新为 `COLD + ONLINE + READ_ONLY`。
5. 用户在订单文件页搜索目标订单；若目标包存在于 A，管理员可直接创建线上恢复任务。
6. 恢复任务从 A 读取 ZIP，解压到受控临时目录，逐文件上传 COS，提交线上恢复会话；完成或失败后清理临时解压目录。

此流程不经过“冷备导入区”，也不要求把包复制回任何热备卷。

### 6.3 COLD → HOT 转换

管理员可对已在线的冷备卷执行转换：

- 转为 `HOT + READ_ONLY`：仅作为历史热备读取卷；
- 转为 `HOT + STANDBY`：允许成为自动切换候选；
- 转为 `HOT + ACTIVE`：成为唯一新订单写入卷。

设为 ACTIVE 前，必须检查无运行中备份任务、容量满足阈值、读写校验通过、目录中不存在其他系统卷标记冲突。转换仅改变卷策略，不移动既有包。

## 7. 对现有实现的差距与改造范围

### 7.1 当前实现

现有 `LocalDirectoryArtifactStore` 在 Spring 启动时绑定单一 `storage.hot-root`，所有 `storage_key` 以该根目录解析。`bk_order_package.storage_key` 和 `bk_supplement_file.storage_key` 均没有明确的存储卷外键。

项目已有 `bk_storage_pool`、容量探测历史和空间预留表，但其当前用途是单一 `hot` 容量域的容量预留，并非面向文件副本的多存储卷管理。不能仅修改现有根目录配置来满足 A/B/C 多卷读取。

### 7.2 废弃或迁移的配置

以下业务配置不再在“系统配置”中由管理员直接填写路径：

| 现有配置 | 处置 | 替代方式 |
|---|---|---|
| `storage.hot-root` | 废弃 | 当前 `HOT + ACTIVE` 存储卷 |
| `storage.managed-roots` | 废弃 | 已纳管存储卷白名单与服务端卷路由 |
| `cold.import-root` | 改为兼容能力 | `IMPORT` 类型存储卷，可选启用 |

`storage.backup-reservation-percent` 等容量策略保留为系统配置，但它作用于当前 ACTIVE 卷，而不是某个固定目录。

### 7.3 数据库调整

推荐在既有 `bk_storage_pool` 基础上演进为存储卷主表，或新建 `bk_storage_volume` 后将 `bk_storage_pool` 保留为容量域。优先推荐新建 `bk_storage_volume`，避免把“逻辑卷”与“容量/配额域”混为一谈。

`bk_storage_volume` 至少应包含：

- `volume_code`、`display_name`、`access_type`、`root_path`；
- `volume_fingerprint`、`marker_json`、`capacity_pool_id`；
- `tier`、`mount_status`、`write_status`、`priority`；
- `last_probed_at`、`last_error_code`、`last_error_message`；
- 所有现有通用字段：`id`、`version`、`create_time`、`update_time`、`create_by`、`update_by`、`is_deleted`。

文件定位表调整：

- `bk_order_package` 增加 `storage_volume_id`；
- `bk_supplement_file` 增加 `storage_volume_id`；
- `bk_artifact_location` 增加或改用 `storage_volume_id`，不再仅依赖 `location_type + location_ref_id` 表达真实路径；
- 为 `(storage_volume_id, storage_key)` 建立唯一索引；原仅按 `storage_key` 的唯一约束需迁移；
- 历史数据迁移为一个“legacy-hot”卷，根目录取迁移执行前已生效的热备根路径；迁移完成后不得切换该卷路径来改变历史文件位置。

任务载荷和审计：

- 新建备份任务时固定 `target_storage_volume_id`；
- 冷备写入、冷备导入、线上恢复任务在创建时固定源卷或目标卷；
- 存储卷纳管、状态转换、ACTIVE 切换、挂载确认、自动切换和失败告警均写入操作审计与任务日志。

### 7.4 后端调整

1. 新增 `storage-volume` 领域模块：发现、纳管、探测、挂载确认、状态转换、优先级与 ACTIVE 选择。
2. 将单例 `ArtifactStore` 改为按 `storage_volume_id` 路由的 `ArtifactStoreRouter`；每个文件 I/O 都显式传入卷 ID 与相对键。
3. 订单备份创建阶段锁定目标 ACTIVE 卷；容量预留服务按真实卷/容量域预留，不再固定使用 `hot`。
4. 下载、补传下载、冷备写入、冷备导入、线上恢复均从副本记录取得源卷后路由读取。
5. 统一健康检查：卷目录存在性、读写探针、可用空间、延迟、卷标记一致性；探测异常只更新卷状态和告警，不得误将文件记录删除或改为不存在。
6. 运行中任务与卷状态变更互斥：ACTIVE 切换、禁用、转冷备、删除卷前必须检查任务引用与未释放空间预留。

### 7.5 前端调整

新增“存储卷管理”菜单，替代当前仅支持路径输入的“容量监控”页面。页面至少包括：

- 候选卷扫描列表：路径、类型、容量、可用空间、挂载状态、识别结果；
- 已纳管卷列表：卷名称、层级、写入状态、优先级、健康状态、最后探测、历史包数量与占用；
- 卷详情：标记/指纹、容量历史、引用订单包、当前任务与操作审计；
- 操作：纳管、重新探测、确认挂载、设为 ACTIVE、设为备用、转冷备、转热备、停用；
- 风险操作二次确认，并展示受影响的运行任务和订单包数量。

订单文件列表中应展示包所在卷、卷层级及可访问状态；卷离线时允许查询，但禁用下载/恢复并展示明确提示。

## 8. 可靠性与安全控制

1. 永远不根据盘符自动覆盖既有卷记录；必须匹配卷 UUID / 指纹。
2. 永远不自动将新发现的介质设为 ACTIVE；自动切换只使用已纳管的备用 HOT 卷。
3. 不允许删除仍被订单包、副本记录、运行中任务或空间预留引用的卷。
4. ACTIVE 切换、COLD→HOT、HOT→COLD 必须加数据库乐观锁/互斥锁，保证全局最多一个 HOT ACTIVE 卷。
5. 文件读取必须验证相对路径不能逃逸所属卷根目录，且不能跟随异常符号链接越界。
6. 重新挂载冷备卷后应至少校验卷标记与待恢复 ZIP 的 SHA-256；失败时标记 `UNAVAILABLE` 或副本 `DAMAGED`，不进入线上恢复。
7. 任务执行中卷不可达时，任务日志应记录卷 ID、显示名称、路径（脱敏策略后）、探测结果和可重试建议；不得因记录日志失败而中断主业务。

## 9. 开发与测试分期

### 第一阶段：Windows 多卷可用性（必须）

使用本地目录或多块本地盘模拟 A/B/C，实现卷表、历史数据迁移、按卷文件路由、手动 ACTIVE 切换、离线/重新接入冷备卷直接恢复、存储卷管理页面和审计日志。

### 第二阶段：自动切换与容量策略

实现备用卷优先级、阈值告警、任务创建时自动选择卷、无可用备用卷时暂停与告警。完成 A→B→C 的自动切换集成测试。

### 第三阶段：客户 NAS 适配

根据客户提供的 NAS 认证/挂载方式验证 UNC 或系统级挂载路径，使用实际服务账号执行读写、容量探测、断连恢复和服务重启后的访问测试。若客户要求系统自行管理 NAS 凭据，再独立设计凭据托管与 NAS 连接器，不应混入第一期。

## 10. 验收场景

1. A 为 ACTIVE，备份订单写入 A；切换 B 为 ACTIVE 后，新订单写 B，旧订单仍从 A 下载和恢复。
2. A 离线后，订单页仍能查到其包并提示卷未挂载；重新接入 A 后无需导入即可恢复线上。
3. A 重新接入但盘符变化，系统能通过卷标记匹配 A。
4. 插入未知 U 盘时，系统仅显示候选卷，不能自动写入或读取为历史卷。
5. 当前 ACTIVE 卷低于阈值时，系统仅切到已纳管且健康的备用 HOT 卷；没有候选卷则暂停新任务并告警。
6. 任务运行期间尝试切换 ACTIVE 或停用源卷，系统拒绝操作并指出关联任务。
7. NAS UNC 路径在服务账号下可读写时，行为与本地路径一致；不可达时卷变为 UNAVAILABLE，历史文件记录不丢失。

## 11. 待客户确认项

1. NAS 是以 UNC、系统级映射盘、NAS 客户端挂载还是其他形式提供给 Windows 服务。
2. NAS 共享是否允许服务账号创建卷标记文件和进行原子重命名。
3. 是否准备多个预先纳管的备用热备卷，以启用自动切换。
4. 冷备盘是否保留稳定卷标记文件，及其插拔、盘符分配和运维登记流程。
5. NAS 容量、配额、网络带宽和单文件大小限制。
