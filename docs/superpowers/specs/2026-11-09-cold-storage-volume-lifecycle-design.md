# 本地备份系统：整盘冷备封存与原盘恢复需求说明

## 1. 文档目的

本文定义本地备份系统冷备模块的新业务语义、完整流程、状态约束、数据一致性要求、界面要求和验收标准，作为后续技术设计、实施计划、开发和测试的依据。

本文确认并覆盖此前“选择部分订单包复制到另一块冷备卷，再清理热备副本”的冷备方案。新方案中的冷备不是文件搬运，也不是生成冷备批次压缩包，而是：

> 将一块已经承载订单备份文件的热备存储卷整体封存为只读冷备介质，拔出后离线保管；需要恢复订单时，重新插入原物理盘并由管理员确认挂载，系统直接从原盘下载订单备份文件或执行线上恢复。

## 2. 背景与问题

订单备份持续写入当前活动热备卷。随着容量增长，管理员需要启用新的热备卷继续接收备份，并将旧热备盘整体拔出、离线保存。旧盘上的订单文件不能被复制、移动或重新打包，否则会产生额外空间、时间和数据一致性成本。

冷备盘离线后，数据库仍必须知道：

- 哪些订单和文件位于该盘；
- 每个文件在盘内的相对位置；
- 该盘的系统身份、管理员备注和离线存放信息；
- 盘内订单的业务创建时间范围；
- 介质当前在线还是离线，能否下载或恢复。

当前实现中的 `COLD_WRITE`、冷备批次、热备清理和冷备导入区属于另一套语义，不能满足整盘封存需求；当前“转冷备”也仅修改卷状态，且会拒绝仍有活动文件副本的卷，因此需要重新设计。

## 3. 已确认的业务决策

1. 冷备导出是整盘封存，不复制、不移动、不重新打包订单文件。
2. 系统正常运行阶段必须存在且只能存在一块 `HOT/ACTIVE` 存储卷。
3. 第一次成功纳管的健康、在线、可写存储卷自动成为 `HOT/ACTIVE`，无需管理员再次操作。
4. 当前 `HOT/ACTIVE` 卷转冷备前，管理员必须选择另一块符合条件的卷接替 `HOT/ACTIVE`。
5. 只要存在任何与源卷或接替卷相关的未终结任务、读取引用或空间预留，立即拒绝操作；系统不排队等待，也不在任务结束后自动转换。
6. 点击“转冷备”后，系统自动完成接替卷切换、内容统计和全量完整性检查；全部通过才将原卷转为冷备。
7. 完整性检查失败时，接替卷继续保持 `HOT/ACTIVE`，原卷保持 `HOT/READ_ONLY`，等待管理员处理；不得自动回切或自动重试。
8. 冷备介质的物理标签内容、打印和粘贴由管理员线下自行管理，系统不控制标签格式。
9. 转冷备时管理员必须至少填写一项用于线下查找介质的备注信息。
10. 冷备内容周期按盘内订单的业务创建时间 `order_created_at` 统计，不按备份时间或文件写入时间统计。
11. 冷备盘拔出前由管理员执行“准备离线”；系统检查没有读取任务后将卷标记为离线，并提示管理员在操作系统中安全弹出。
12. 冷备盘重新插入后不自动启用；必须由管理员手动执行“确认挂载”。
13. 重新挂载成功后，订单下载和线上恢复直接读取原冷备盘，不先复制回热备区。
14. 临时导入区、选择性复制回热备卷等冗余方案不属于本期范围，待主流程全部实现并验证后另行设计。

## 4. 目标、非目标与反目标

### 4.1 目标

- 支持将一整块历史热备卷安全封存为冷备卷。
- 保证切换过程中始终有一块健康的 `HOT/ACTIVE` 卷承接新备份。
- 在封存前验证盘内所有受管订单文件的数据完整性。
- 冷备离线后仍可按订单号查询并准确定位物理介质。
- 冷备原盘重新接入后可直接下载和执行线上恢复。
- 保证任务、订单、文件和存储卷状态展示一致且可追溯。
- 防止盘符变化、盘符复用或错误介质接入造成数据误读。

### 4.2 本期非目标

- 不把部分订单从热备卷复制到另一块冷备卷。
- 不创建冷备批次 ZIP、`batch-manifest.json` 或 `_COMPLETE` 归档。
- 不执行冷备覆盖后的热备文件删除。
- 不提供临时导入区扫描和选择性回迁。
- 不自动识别并启用刚插入的冷备盘。
- 不自动打印或约束物理标签内容。
- 不自动在任务结束后继续此前被拒绝的转冷备操作。

### 4.3 反目标

以下结果即使功能表面可用，也视为需求失败：

- 转冷备过程中出现没有 `HOT/ACTIVE` 卷或同时存在多个 `HOT/ACTIVE` 卷；
- 修改卷层级后批量改写订单文件路径，导致数据库位置与物理位置不一致；
- 冷备离线时删除订单、文件或副本位置记录；
- 仅凭 Windows 盘符识别冷备介质；
- 完整性检查失败后仍把原卷标记为 `COLD`；
- 冷盘离线时仍允许创建必然无法读取的下载或恢复任务；
- 用任务执行时的历史状态覆盖存储卷当前真实状态。

## 5. 术语与事实来源

### 5.1 存储卷

存储卷是系统已纳管的受控目录及其物理介质身份。每个卷具有不可变的系统身份标记、卷 ID 和卷内根路径。

### 5.2 文件定位

任一订单包或补传文件必须使用下列组合定位：

```text
storage_volume_id + storage_key
```

其中 `storage_key` 是卷内相对路径。卷转换为冷备、离线或重新挂载时，不改变该组合，也不移动物理文件。

### 5.3 当前状态与历史快照

- `bk_storage_volume` 是卷当前层级、挂载状态和写入状态的唯一事实来源。
- 订单、订单包、补传文件和副本台账只保存卷 ID 与相对路径，不重复持久化卷的当前状态。
- 页面查询时关联卷表，实时展示当前 `HOT/COLD` 和 `ONLINE/OFFLINE` 状态。
- 任务保留执行当时的卷名称、层级和路径快照用于审计，但历史快照不得作为当前文件路由依据。

### 5.4 管理员查找信息

系统身份和线下查找信息相互独立：

- 系统身份：卷 UUID、卷标记和可获取的物理指纹，不可由管理员随意修改，用于防误接管。
- 查找信息：卷别名、线下标签备注、存放位置和其他说明，用于管理员找到物理盘，不参与身份认证或文件路由。

系统不负责打印物理标签。管理员可在线下标签上写任何内容。

### 5.5 补充术语

- **稳定卷代码**：系统内长期不变、用于展示和检索的卷代码；它不是盘符，也不作为唯一身份校验凭据。
- **受管文件**：由订单包、补传文件或文件副本台账中的有效位置记录声明，且位于存储卷受控数据命名空间内的文件。
- **有效位置记录**：未逻辑删除，生命周期为 `ACTIVE`，物理状态为 `PRESENT`，并具有卷 ID、规范相对路径、非负大小和合法 SHA-256 的位置记录。
- **卷健康**：卷标记匹配、目录可访问，且针对其用途满足读或写探针；健康结论必须带探测时间，不能永久复用历史结果。
- **副本健康**：位置记录有效，所属卷可读，文件最近一次校验没有失败；任务实际使用前仍须进行本需求规定的目标文件校验。
- **封存尝试**：一次管理员发起的、具有独立编号和不可变结果的卷封存执行。失败后重新操作会产生新的尝试。
- **读取租约**：下载、恢复或校验在读取卷之前持久化取得的短期占用记录，用于阻止卷离线或转换。

## 6. 存储卷状态模型

### 6.1 状态维度

| 维度 | 状态 | 含义 |
|---|---|---|
| 层级 `tier` | `HOT` | 热备卷，可作为备份写入候选或历史只读卷 |
|  | `COLD` | 已整体封存的冷备卷，只读，不接收新备份 |
| 挂载 `mount_status` | `ONLINE` | 已确认挂载且当前允许系统访问 |
|  | `OFFLINE` | 已由管理员准备离线或尚未确认重新挂载 |
|  | `UNAVAILABLE` | 预期在线但探测失败、标记异常或访问异常 |
| 写入 `write_status` | `ACTIVE` | 唯一的新订单备份写入目标，仅允许 `HOT/ONLINE` |
|  | `STANDBY` | 已纳管的热备候选卷，可被选择为接替卷 |
|  | `READ_ONLY` | 只允许读取，不接收新备份 |
|  | `DISABLED` | 停用，不参与自动路由 |

另设行政生命周期 `admin_status`：`ENABLED` 表示正常管理，`RETIRED` 表示已经退役且只保留历史。它不替代挂载、层级或写入状态。特别是 COLD 卷退役后仍保持 `write_status=READ_ONLY`，通过 `admin_status=RETIRED` 排除路由。

### 6.2 合法核心组合

| 组合 | 用途 |
|---|---|
| `HOT/ONLINE/ACTIVE` | 唯一活动热备卷 |
| `HOT/ONLINE/STANDBY` | 可选接替热备卷 |
| `HOT/ONLINE/READ_ONLY` | 历史热备卷，或封存检查失败后待处理卷 |
| `COLD/ONLINE/READ_ONLY` | 已封存且仍插入，或重新确认挂载的冷备卷 |
| `COLD/OFFLINE/READ_ONLY` | 已拔出并离线保管的冷备卷 |
| `COLD/UNAVAILABLE/READ_ONLY` | 介质预期存在但身份或访问检查失败 |
| `HOT/UNAVAILABLE/ACTIVE` | 活动卷意外不可用的故障状态；保留角色但禁止新备份并告警 |
| `HOT/ONLINE/DISABLED` | 已停用但仍在线的卷，不参与自动路由 |
| `COLD/OFFLINE/READ_ONLY + RETIRED` | 已退役的离线冷备卷，仅保留历史台账 |

`COLD/ACTIVE`、`COLD/STANDBY` 均为非法组合。冷备卷永远不能成为新备份写入目标。

### 6.3 全局不变量

1. 存在已纳管健康存储体系时，必须且只能有一个 `HOT/ONLINE/ACTIVE`。
2. 任何状态切换不得绕过活动卷唯一性约束。
3. `COLD` 必须是 `READ_ONLY`。
4. `OFFLINE` 或 `UNAVAILABLE` 卷不能作为文件读取结果返回。
5. 卷状态变化不改变文件归属卷和相对路径。
6. 已经固化源卷或目标卷的运行中任务必须阻止相关卷状态转换。

系统首次部署、尚未纳管任何卷，或发生不可控硬件故障导致唯一活动卷突然不可用时，可以暂时不存在可用 `HOT/ACTIVE`；此时系统属于降级故障状态，必须阻止新备份并产生告警，不能把该异常当成正常运行状态。

### 6.4 卷操作状态

长时间封存和离线操作不能只依赖上述三个业务状态。存储卷还必须有持久化的操作状态或等价的卷级操作占用：

| 操作状态 | 含义 | 新写入 | 新读取 | 其他生命周期操作 |
|---|---|---|---|---|
| `IDLE` | 无卷级操作 | 按业务状态 | 按业务状态 | 允许 |
| `SEALING` | 正在生成封存清单或全量校验 | 禁止 | 禁止从该卷建立新租约 | 禁止 |
| `GOING_OFFLINE` | 正在准备离线 | 禁止 | 禁止建立新租约 | 禁止 |
| `MOUNTING` | 正在确认挂载 | 禁止 | 禁止 | 禁止 |
| `REPAIR_REQUIRED` | 封存失败，等待处理 | 禁止 | 禁止业务读取，仅允许受审计诊断 | 只允许重试、放弃或退役 |

操作状态必须由数据库条件更新或卷级锁保护。文件路由器和任务创建服务必须检查它，不能只由前端隐藏按钮。

### 6.5 状态转换表

| 事件 | 起始状态 | 前置条件 | 处理中 | 成功状态 | 失败状态 |
|---|---|---|---|---|---|
| 首卷纳管 | 无活动卷 | 卷健康、在线、可写、容量合格 | 纳管事务 | `HOT/ONLINE/ACTIVE + IDLE` | 不可写且非 ACTIVE |
| 后续纳管 | 已有活动卷 | 卷健康、在线、可写 | 纳管事务 | `HOT/ONLINE/STANDBY + IDLE` | 不可写且非 STANDBY |
| 独立切换活动卷 | A `HOT/ONLINE/ACTIVE`，B `HOT/ONLINE/STANDBY` | 无相关任务/租约/预留 | 同一短事务 | A `HOT/ONLINE/READ_ONLY`，B `HOT/ONLINE/ACTIVE` | 全部回滚 |
| ACTIVE 卷开始封存 | A ACTIVE，B STANDBY | 满足第 8 节全部条件 | A `HOT/READ_ONLY + SEALING`，B ACTIVE | 进入封存校验 | 全部回滚或形成明确失败尝试 |
| READ_ONLY 卷开始封存 | A `HOT/ONLINE/READ_ONLY` | 已有其他唯一 ACTIVE；无阻塞项 | A `SEALING` | 进入封存校验 | A 保持原状态 |
| 封存校验成功 | A `HOT/READ_ONLY + SEALING` | 清单冻结且全量通过 | `COMMITTING` | A `COLD/ONLINE/READ_ONLY + IDLE` | A `HOT/READ_ONLY + REPAIR_REQUIRED` |
| 封存校验失败/取消 | A `HOT/READ_ONLY + SEALING` | 发现异常或管理员取消 | 结束当前尝试 | A `HOT/READ_ONLY + REPAIR_REQUIRED` | 同左 |
| 重试封存 | A `HOT/READ_ONLY + REPAIR_REQUIRED` | 另有唯一 ACTIVE；问题已处理 | 新 attempt，A `SEALING` | COLD/ONLINE/READ_ONLY | 回到 REPAIR_REQUIRED |
| 准备离线 | COLD/ONLINE/READ_ONLY | 无租约、标记匹配 | `GOING_OFFLINE` | COLD/OFFLINE/READ_ONLY + IDLE | 回到 COLD/ONLINE/READ_ONLY + IDLE |
| 确认挂载 | COLD/OFFLINE/READ_ONLY | 管理员选中候选路径、身份匹配 | `MOUNTING` | COLD/ONLINE/READ_ONLY + IDLE | OFFLINE 或 UNAVAILABLE + IDLE |
| 意外失联 | 任一预期在线卷 | 健康探测连续失败 | 告警 | 保留 tier/write，mount=UNAVAILABLE | 不自动改变文件位置 |
| HOT 卷停用/放弃 | 非 ACTIVE HOT 卷 | 无任务、租约、预留 | 短事务 | write=DISABLED，保留历史记录 | 原状态 |
| COLD 卷退役 | COLD/READ_ONLY | 无任务、租约、预留 | 短事务 | admin=RETIRED，write 仍为 READ_ONLY | 原状态 |
| 原 ACTIVE 恢复在线 | HOT/UNAVAILABLE/ACTIVE | 管理员选择路径，身份、健康、写入和容量校验通过 | MOUNTING | HOT/ONLINE/ACTIVE | 保持 UNAVAILABLE/ACTIVE |
| ACTIVE 故障切换 | A HOT/UNAVAILABLE/ACTIVE，B HOT/ONLINE/STANDBY | 管理员确认；A 无存活租约，B 健康 | 同一短事务 | A HOT/UNAVAILABLE/READ_ONLY，B HOT/ONLINE/ACTIVE | 全部回滚 |
| 故障切换后的原卷恢复 | A HOT/UNAVAILABLE/READ_ONLY | 管理员选择路径，身份匹配且目录可读 | MOUNTING | A HOT/ONLINE/READ_ONLY | 保持 UNAVAILABLE/READ_ONLY |

除首次纳管外，所有状态变更均由管理员触发；意外失联只更新健康状态和告警，不自动执行封存、接管或文件搬迁。

活动卷意外失联后，存储卷管理页必须提供两个明确入口：原盘重新接入时“确认活动卷挂载”，以及存在健康 STANDBY 时“故障切换”。故障切换不执行冷备封存，也不宣称 A 内容完整；故障切换后 A 再接入时必须执行“确认历史热备卷挂载”，身份和可读性校验通过后只恢复为 `HOT/ONLINE/READ_ONLY`，绝不自动抢回 ACTIVE，后续再另行校验或封存。

## 7. 首次纳管与后续纳管

### 7.1 首个卷自动激活

首次纳管卷成功后，如果系统不存在任何未删除的 `HOT/ACTIVE` 卷，系统应在同一受控流程中：

1. 创建并校验卷标记；
2. 验证目录在线、可写；
3. 探测总容量和可用容量；
4. 确认容量未达到禁止写入阈值；
5. 将该卷设置为 `HOT/ONLINE/ACTIVE`；
6. 记录“首次卷自动激活”审计事件。

任一步失败时，纳管操作不得伪造 `ACTIVE`。应返回明确错误；如果卷记录已创建，必须处于不可写状态并允许管理员修复或重新探测。

并发纳管多个首卷时，必须通过数据库锁和唯一约束保证只有一个卷成为 `ACTIVE`。

### 7.2 后续卷默认状态

已有活动卷时，新纳管的健康可写卷默认进入 `HOT/ONLINE/STANDBY`，不得自动抢占当前活动卷。管理员可以后续将其选择为活动卷或转为其他允许状态。

## 8. 热备整盘转冷备流程

### 8.1 操作入口

管理员可以对以下两类源卷发起封存：

- 当前 `HOT/ACTIVE`：必须选择接替卷，系统先完成活动卷切换再封存原卷；
- `HOT/READ_ONLY`：系统中必须已经存在另一块唯一 `HOT/ACTIVE`，不再要求选择或切换接替卷。

封存失败后的 `HOT/READ_ONLY + REPAIR_REQUIRED` 使用“重新封存”入口。它创建新的封存尝试并重新执行全量检查，不重复切换当前活动卷。系统打开转冷备确认页，不允许通过普通状态更新接口绕过封存流程。

### 8.2 管理员输入

当前 ACTIVE 卷封存时，管理员必须：

1. 从符合条件的候选卷中选择一块接替 `HOT/ACTIVE` 的卷；
2. 至少填写一项非空查找备注。

READ_ONLY 卷首次封存或失败后重新封存时，只要求系统已有另一块唯一健康 ACTIVE 卷，并要求备注非空；当前 ACTIVE 卷作为运行保障被记录到封存尝试中，但不被重复切换。

建议提供以下字段，但不控制管理员线下标签内容：

- `archive_note`：冷备查找备注，必填；
- `display_name`：卷别名，可沿用或修改；
- `offline_label_note`：线下标签备注，可选；
- `physical_location`：计划存放位置，可选；
- `remark`：其他说明，可选。

“至少填写一个备注信息”由 `archive_note` 统一满足，避免多个可选字段组合产生含糊校验。

### 8.3 转换前预览

确认页必须在提交前展示：

- 原卷名称、卷 ID、当前层级、挂载状态和写入状态；
- 接替卷名称、容量和健康状态；
- 原卷订单数量、订单文件数量和受管数据总量；
- 原卷内订单最早和最晚业务创建时间；
- 建议周期文本，例如 `20260101-20260315`；
- 当前相关运行任务数、读取引用数和空间预留数；
- 将要执行的步骤及失败后的状态。

预览数据用于管理员决策，提交后必须重新校验，不能仅信任浏览器展示的旧数据。

### 8.4 接替卷条件

接替卷必须同时满足：

- 已纳管且未删除；
- 已经是 `HOT/ONLINE/STANDBY`；
- 卷标记和物理身份校验通过；
- 服务账号可读写；
- 容量健康且未达到配置的切换阈值；
- 没有运行中写入任务、读取任务或活动空间预留；
- 不是原卷，也不是冷备或导入卷；
- 未被其他封存或生命周期操作占用。

源卷已是 `HOT/READ_ONLY` 时，本节不要求重新选择 STANDBY；但当前唯一 ACTIVE 卷仍须在线且健康，并在本次封存尝试结束前持有生命周期操作保留，禁止被转冷备、停用或切换为非 ACTIVE。它可以继续承接正常订单备份。

### 8.5 任务互斥

只要原卷或接替卷存在以下任何情况，转冷备请求立即失败：

- 状态为 `CREATED`、`RUNNING`、`RETRYING_FAILED_ORDERS`、取消处理中或其他非终态的备份任务；
- 从原卷读取的线上恢复任务；
- 正在从原卷执行的下载、校验、导出或其他文件读取；
- 目标为原卷或接替卷的写入任务；
- 尚未释放的空间预留；
- 其他存储卷切换、封存、确认挂载或准备离线操作。

成功、彻底失败和已取消是可接受的终态。部分失败但仍允许重试的任务不属于终态。

被拒绝的操作不建立后台等待，也不监听任务结束。管理员必须在问题消失后重新点击“转冷备”。错误信息应列出阻塞任务编号、类型、状态及与卷的关系。

### 8.6 安全切换与冻结

封存当前 ACTIVE 卷时，系统以数据库事务和卷级互斥完成以下动作：

1. 重新验证所有前置条件；
2. 锁定当前活动卷、接替卷和活动卷选择记录；
3. 阻止新的备份任务继续选择原卷；
4. 在事务内部先把原卷降为 `HOT/ONLINE/READ_ONLY`；
5. 再将接替卷设置为 `HOT/ONLINE/ACTIVE`；
6. 将原卷操作状态设置为 `SEALING`，并对接替卷登记生命周期操作保留；
7. 创建卷封存检查任务并记录源卷、接替卷、操作者和输入快照；
8. 提交事务后开始文件系统检查。

数据库切换必须在同一事务中完成：事务内先降原卷再升接替卷，以兼容即时唯一约束；其他事务只能看到提交前或提交后的完整状态，不能看到中间的零 ACTIVE 状态。任一步失败必须整体回滚。新建备份任务与活动卷切换必须使用相同的锁顺序，避免任务在切换缝隙中绑定错误目标卷。

原卷进入只读后不得自动回到 `ACTIVE`。即使后续检查失败，新备份仍继续写入接替卷。

源卷已为 HOT/READ_ONLY 时，系统跳过活动卷切换，仅在短事务中复核唯一 ACTIVE、把源卷置为 `SEALING`、登记操作保留并创建新的封存尝试。

`SEALING` 建立后，文件路由器不得从源卷创建新的业务读取租约，源卷也不得参与其他状态转换。封存前置检查已保证不存在旧租约，因此校验期间文件集合不会受到应用内部并发读写影响。

### 8.7 封存内容统计

系统在进入 `SEALING` 后冻结一份不可变的封存清单。清单来源包括原卷上的订单包、补传文件和有效副本位置记录，并按 `(storage_volume_id, storage_key)` 去重。若同一路径的多个记录在大小、摘要或制品归属上冲突，封存失败。

有效记录的精确条件为：未逻辑删除、生命周期为 `ACTIVE`、物理状态为 `PRESENT`、业务制品自身处于可用状态，且卷 ID、相对路径、大小和 SHA-256 完整合法。`RETIRED`、`DAMAGED`、`ABSENT`、临时替换中和逻辑删除记录不进入成功清单，但必须作为异常或排除项记录在报告中。

封存阻断矩阵如下：

| 记录或文件情况 | 是否进入校验清单 | 是否阻断封存 |
|---|---:|---:|
| `ACTIVE + PRESENT` 且业务制品可用 | 是 | 校验失败时阻断 |
| `DAMAGED`、`ABSENT` | 否 | 是，即使同一制品在其他卷还有健康副本 |
| `REPLACING` 或临时替换中 | 否 | 是，必须先完成或回滚替换 |
| `RETIRED` 或逻辑删除记录 | 否 | 否，但记录为排除项 |
| 受控业务命名空间中的孤立普通文件 | 否 | 是 |
| 明确排除的卷标记、系统元数据、日志和临时目录 | 否 | 否 |

因此 `DAMAGED`、`ABSENT`、替换中记录和业务目录孤立文件均不是可由实施者自行选择的策略，必须阻断封存。

系统基于该冻结清单统计并持久化：

- 去重订单数量；
- 订单包数量；
- 补传文件及其他受管文件数量；
- 文件总字节数；
- 最早和最晚订单业务创建时间 `order_created_at`；
- 周期显示文本 `yyyyMMdd-yyyyMMdd`；
- 内容清单摘要；
- 统计时间和数据版本。

同一订单存在多个受管文件时，订单数量只计算一次，文件数量按实际文件记录计算。订单周期只统计在该卷上拥有有效订单备份文件的订单，不得查询全库订单后直接取范围。

无法关联订单、缺失 `order_created_at`、重复冲突位置或路径不合法均应进入异常报告，不能静默忽略。

封存清单必须包含清单版本、生成时数据库版本或时间水位、规范排序后的条目及整体 SHA-256。校验期间禁止修改清单涉及的位置台账；最终提交前必须复核清单摘要和相关记录版本未变化。

孤立文件扫描范围限定为受控数据命名空间，例如 `orders/`、`supplements/` 和实施方案明确的业务目录；卷标记、系统元数据、已知临时目录和日志目录必须列入明确排除表。命名空间中的未登记普通文件默认阻断封存并进入报告。

### 8.8 全量完整性检查

系统必须检查原卷上的所有有效受管文件，而不是抽样检查。每个文件至少验证：

1. `storage_volume_id` 指向原卷；
2. `storage_key` 是规范化相对路径，解析后不能逃逸受控根目录；
3. 文件存在且为允许的普通文件；
4. 实际大小与台账一致；
5. 实际 SHA-256 与台账一致；
6. 订单 ZIP 可正常打开，包含预期清单且清单摘要正确；
7. 补传文件和普通制品按其台账大小、SHA-256 和允许文件类型验证，不套用 ZIP 结构检查；
8. 文件不是符号链接、junction、reparse point 或会逃逸卷根的链接；硬链接必须按实施阶段明确的同卷安全规则处理，默认拒绝；
9. 文件可通过独占受控读取句柄稳定读取；
10. 同一物理路径不存在相互矛盾的活动记录。

检查过程必须持久化总数、已完成数、成功数、失败数、当前文件和失败明细。管理员关闭浏览器或服务短暂重启不能丢失已生成的失败报告。

任何一项异常都使本次封存失败。不得因为多数文件通过就把卷标记为 `COLD`。

受控根目录的威胁模型是：备份服务是业务数据的唯一写入者，封存期间管理员和外部程序不得修改目录。系统通过 `READ_ONLY + SEALING` 阻止自身写入，并在最终提交前复核清单记录版本、文件大小和修改时间；如果客户环境允许外部程序绕过系统修改文件，则系统不能提供跨文件系统快照级保证，必须通过目录 ACL、只读挂载或存储快照能力额外约束。

### 8.9 封存任务状态机与恢复

每次封存尝试具有独立 attempt 编号和以下持久化阶段：

```text
REQUESTED
  → SWITCHED
  → MANIFEST_FROZEN
  → VERIFYING
  → COMMITTING
  → SUCCEEDED
```

终止或异常状态包括：

- `VERIFY_FAILED`：发现内容异常，业务失败，不自动重试；
- `COMMIT_FAILED`：校验通过但最终数据库提交失败，需要管理员查看后重新发起；
- `CANCELLED`：管理员取消，同样留下 HOT/READ_ONLY；
- `INTERRUPTED`：执行进程失联，等待同一 attempt 恢复；
- `ABANDONED`：管理员明确放弃该失败尝试，保留历史报告。

任务按文件条目持久化 checkpoint、当前清单版本、runner lease/epoch、心跳和已完成结果。服务崩溃后，新的执行器只能在旧 runner lease 过期后接管同一个 attempt，并从已验证条目的下一个安全点继续；当前正在处理但未提交结果的单个文件必须从头校验。该行为属于同一尝试的故障恢复，不是业务自动重试。

业务校验失败、管理员取消或最终提交失败后，系统绝不自动创建新 attempt。管理员必须处理问题并点击“重新封存”。取消在当前文件安全点生效；取消后接替卷保持 ACTIVE，源卷进入 `REPAIR_REQUIRED`。

### 8.10 成功提交

全部检查通过后，系统在事务中：

1. 确认原卷仍为本次任务冻结的 `HOT/READ_ONLY`；
2. 确认接替卷仍为唯一 `HOT/ACTIVE`；
3. 将原卷改为 `COLD/ONLINE/READ_ONLY`；
4. 保存不可变的封存快照和内容清单摘要；
5. 保存管理员查找备注；
6. 更新卷最近完整校验时间；
7. 记录成功审计事件。

同一最终提交事务还必须把封存 attempt/phase 更新为 `SUCCEEDED`，把源卷操作状态恢复为 `IDLE`，释放接替 ACTIVE 卷的生命周期操作保留，并终结 runner lease。事务失败则上述变化全部回滚；恢复执行器依据 attempt phase 重新判断，不会遇到“卷已是 COLD 但任务仍在 VERIFYING”的半完成状态。

该过程不创建新文件副本，不修改订单包的 `storage_volume_id` 或 `storage_key`，也不把原位置标记为删除。

### 8.11 失败处理

完整性检查或最终提交失败时：

- 接替卷保持 `HOT/ONLINE/ACTIVE`；
- 原卷保持 `HOT/ONLINE/READ_ONLY`；
- 原卷不得标记为 `COLD`；
- 保存失败阶段、异常文件、预期值、实际值和建议处理方式；
- 不自动回切活动卷；
- 不自动重试；
- 管理员修复后必须重新发起“转冷备”，系统重新执行全部前置检查和全量完整性检查。

失败尝试是不可变历史记录。管理员处理文件后点击“重新封存”，系统对 `HOT/READ_ONLY + REPAIR_REQUIRED` 原卷创建新 attempt，不重复切换 ACTIVE。系统本期不提供任意文件编辑器；管理员可在受控维护窗口从可信来源修复物理文件，数据库摘要或位置台账只能通过后续实施定义的受审计对账工具修正，不能直接在页面手工填写。无法修复时可以放弃尝试并停用该卷，但不能把它伪装成健康冷备。

服务崩溃按第 8.9 节恢复同一 attempt；只有明确的业务失败、取消或提交失败才进入待人工处理状态。状态不明的卷绝不能自动标记为冷备。

失败、取消或放弃也必须通过短事务原子完成：写入 attempt 终态和报告摘要、将源卷设置为 `HOT/READ_ONLY + REPAIR_REQUIRED`、释放 ACTIVE 卷生命周期操作保留并终结 runner lease。若该收尾事务失败，attempt 保持可接管的非终态，由恢复执行器重做收尾，不能只改其中一部分。

## 9. 冷备准备离线与物理拔出

### 9.1 操作入口

只有 `COLD/ONLINE/READ_ONLY` 卷显示“准备离线”按钮。

### 9.2 前置检查

系统必须确认：

- 没有从该卷读取的下载、线上恢复或校验任务；
- 没有未释放的文件句柄或系统登记的读取租约；
- 没有其他卷生命周期操作；
- 最近封存检查成功且封存快照存在；
- 卷标记仍匹配。

存在阻塞项时立即拒绝并列出详情，不自动等待。

“准备离线”必须使用防竞态协议：在卷级短事务中锁定卷，将操作状态从 `IDLE` 条件更新为 `GOING_OFFLINE`，从这一刻开始拒绝新读取租约，然后检查并锁定现有有效租约。若仍有租约，事务回滚为 `IDLE` 并返回阻塞详情；若没有租约，才提交 OFFLINE。不能采用“先查租约为空、稍后再改 OFFLINE”的分离步骤。

### 9.3 状态变化与提示

检查通过后：

1. 将卷更新为 `COLD/OFFLINE/READ_ONLY`；
2. 使新的读取路由立即不再选择该卷；
3. 记录准备离线时间和操作人；
4. 提示管理员在 Windows 或存储设备管理工具中安全弹出后再拔盘。

应用系统不宣称已经完成操作系统级安全弹出，除非后续明确实现并验证相应平台能力。物理盘仍插着但已“准备离线”时，系统也必须按离线处理，不能继续读写。

管理员尚未物理拔盘时，可以执行“撤销准备离线”。系统必须重新验证同一卷标记后，按确认挂载流程恢复为 `COLD/ONLINE/READ_ONLY`，不能由健康探测调度器自动改回 ONLINE。未经“准备离线”直接拔盘时，健康探测将其标记为 `UNAVAILABLE` 并告警；数据库文件位置保持不变。读取过程中介质意外消失时，当前操作失败、释放租约并记录卷级与文件级错误。

## 10. 冷备盘重新接入与确认挂载

### 10.1 发现但不自动启用

冷盘重新插入后，候选卷扫描可以发现对应路径，但系统不得自动把它改为在线，也不得自动创建读取任务。

管理员必须在原冷备卷记录上执行“确认挂载”，或从扫描结果中选择“匹配已有冷备卷”。

### 10.2 身份校验

确认挂载必须验证：

- 受控目录中的卷 UUID 标记与数据库记录一致；
- 标记格式和校验信息有效；
- 可获取时，物理卷指纹与历史记录不存在冲突；
- 路径可访问且受控根目录存在；
- 卷为只读使用时至少可读；
- 盘符变化不会影响识别；
- 相同盘符插入其他介质时不能误匹配。

标记缺失、损坏、冲突或身份不一致时，将卷保持 `OFFLINE` 或标记为 `UNAVAILABLE`，并要求管理员处理；不得重写新标记后强行接管。

卷 UUID 标记是必须完全匹配的主身份，历史物理指纹是附加防护：已记录且当前可获取的指纹不一致时必须拒绝；因设备或驱动限制暂时无法取得指纹时，必须记录降级审计并由管理员二次确认。若同一 UUID 同时出现在多个候选路径，视为标记复制或重复挂载冲突，全部拒绝在线，不能任选其一。

### 10.3 成功状态

确认成功后将卷更新为：

```text
COLD / ONLINE / READ_ONLY
```

确认挂载请求必须携带管理员选中的候选挂载点和既有卷 ID。系统在卷锁内验证该路径没有绑定其他在线卷，并原子更新该卷当前可路由的 `mount_path/root_path` 绑定、容量、最后探测时间和审计日志。历史路径保留在审计中，但不得修改订单文件的卷 ID 和相对路径。同一卷不允许同时存在两个活动挂载绑定。

### 10.4 使用前校验

重新挂载不要求先把整盘复制回热备卷。下载或线上恢复读取具体订单包前，应通过同一个稳定只读句柄验证目标文件存在、大小和 SHA-256；验证完成后将句柄位置复位，再从该句柄读取或解包，避免校验与使用之间重新打开文件产生竞态。大文件校验必须展示进度并使用独立于普通网络请求的可配置超时；不能采用已经向客户端发送数据后才发现摘要错误、却仍宣称“读取前校验”的实现。

校验失败时：

- 拒绝本次下载或恢复；
- 将对应副本标记为损坏或异常；
- 展示卷、订单和文件级错误；
- 不影响同卷其他尚未证明损坏的文件，但应产生介质健康告警。

## 11. 订单查询、下载与线上恢复

### 11.1 离线订单可检索

冷备卷离线不能导致订单、快照、订单包、文件清单或位置台账被删除。用户仍可在“订单文件”和“订单备份”中按订单号、公开订单号等现有条件查询。

对于只位于离线冷备卷的订单，列表和详情至少显示：

- 订单号和订单创建时间；
- 存储状态“冷备离线”；
- 存储卷名称、卷 ID 或稳定卷代码；
- 管理员查找备注；
- 线下标签备注和存放位置（若填写）；
- 冷备周期，例如 `20260101-20260315`；
- 卷内相对位置；
- “请插入对应介质并在存储卷管理中确认挂载”的操作提示。

### 11.2 操作可用性

- 目标订单存在任一健康在线副本时，系统选择可读副本并允许下载或恢复。
- 只有离线冷备副本时，禁用下载和线上恢复入口，或在提交时返回明确的“介质离线”业务错误；不能创建必然失败的后台任务。
- 冷备卷确认挂载后，无需改写订单记录，操作入口应立即恢复可用。
- 多副本场景下应优先选择健康在线副本，并在任务创建时固化实际源卷和相对路径。

多副本确定性优先级为：有效且健康的 `HOT/ONLINE` 副本优先，其次是 `COLD/ONLINE/READ_ONLY`；同一层级按最近成功校验时间降序、稳定副本 ID 升序选择。处于 `SEALING`、`GOING_OFFLINE`、`MOUNTING`、`REPAIR_REQUIRED` 的卷不作为新业务读取候选。页面聚合状态应分别展示“存在在线可读副本”“仅冷备离线”“部分副本异常”“无可用副本”，并允许在详情查看所有副本，不能用一个异常副本覆盖其他健康副本。

### 11.3 本地下载

本地下载直接从 `COLD/ONLINE/READ_ONLY` 卷流式读取订单包。下载期间必须登记短期读取引用，使“准备离线”和其他破坏性状态转换能够检测并拒绝操作。

取得下载源必须在一个受控事务中完成：锁定候选卷，复核卷仍在线且操作状态允许读取，解析并固化副本，然后插入读取租约。响应结束、客户端断开或发生异常时都必须释放租约。

### 11.4 线上恢复

线上恢复任务创建时必须：

1. 解析健康在线副本；
2. 固化 `source_storage_volume_id` 和 `source_storage_key`；
3. 建立任务与源卷引用；
4. 校验订单包后再执行解包和上传；
5. 在成功、失败或取消后可靠释放读取引用和临时文件。

任务执行期间冷备卷不得准备离线、停用或改变层级。

线上恢复、后台校验和其他所有读取类型必须复用第 11.3 节同一套原子取源协议：锁定候选卷、复核 ONLINE 和操作状态、固化副本并插入租约必须在一个受控事务内完成。不能先选择源卷、提交事务后再补建租约。

### 11.5 读取租约协议

读取租约至少包含：卷 ID、制品 ID、用途、任务或请求 ID、owner/runner epoch、创建时间、心跳时间、到期时间和状态。后台恢复任务定期续租；同步下载在连接存活期间续租或使用有界 TTL。租约只能由持有者正常释放，或由回收器在到期且确认 owner 已失效后回收。

取消处理中的恢复任务在文件句柄关闭、临时目录清理并释放租约之前仍属于卷的阻塞任务。服务崩溃后，租约不能永久残留，也不能仅因单次心跳延迟就被提前回收。TTL、心跳间隔和失联判定必须成为具名配置，并满足“TTL 大于至少两个心跳周期”的校验。

## 12. 状态同步与一致性

### 12.1 不批量复制卷当前状态

订单、任务和文件记录不得各自维护一份可变的 `HOT/COLD/ONLINE/OFFLINE` 当前状态。页面和接口通过 `storage_volume_id` 关联存储卷实时状态，避免一次卷转换需要更新成千上万条记录并产生部分成功。

### 12.2 必须持久化的位置关系

以下记录必须保持一致：

- 订单包：`storage_volume_id + storage_key`；
- 补传文件：`storage_volume_id + storage_key`；
- 文件副本台账：制品 ID、卷 ID、相对路径、大小、SHA-256、生命周期；
- 恢复任务订单/文件证据：实际源卷 ID 和源相对路径；
- 备份任务：创建时固化的目标卷 ID；
- 封存快照：源卷、接替卷、内容统计、订单时间范围和清单摘要。

### 12.3 历史任务展示

历史任务应同时展示：

- 执行当时的卷名称、层级等审计快照；
- 当前关联卷的实时状态；
- 实际读写位置。

卷从 HOT 转为 COLD 后，历史备份任务仍应表达“当时写入 HOT 卷”这一历史事实，同时显示“该卷当前已冷备/离线”。不得把历史任务批量改成冷备任务。

### 12.4 事务与并发

- 活动卷切换、首次自动激活、封存最终提交、准备离线和确认挂载必须使用卷级锁或数据库行锁。
- 新建备份任务与活动卷切换必须共享一致的锁顺序。
- 文件读取必须建立可查询的读取引用或租约，不能只依赖进程内计数。
- 状态更新必须使用版本号或条件更新，防止重复点击覆盖并发结果。
- 所有跨数据库与文件系统的操作必须可恢复；不得把长时间文件校验放在长数据库事务内。
- 封存期间对源卷和保障运行的 ACTIVE 卷持有生命周期操作保留；ACTIVE 卷可以继续接收正常备份，但不能再执行 B→C 切换、停用或另一轮封存，直至本次 attempt 终结并释放保留。

## 14. 管理界面需求

### 14.1 存储卷列表

至少展示：

- 卷名称、稳定卷代码；
- `tier / mount_status / write_status`；
- 已用、可用、总容量；
- 订单数量、文件数量、数据量；
- 订单创建时间范围；
- 查找备注和存放位置；
- 最近完整校验时间；
- 当前阻塞任务数量；
- 最近错误。

### 14.2 转冷备确认页

必须展示第 8.3 节的预览信息、接替卷选择、备注输入、风险说明和二次确认。提交后进入可查看进度的封存任务详情。

### 14.3 封存任务详情

展示：

- 当前阶段；
- 总文件数、已检查、成功、失败；
- 已处理字节和总字节；
- 当前文件；
- 源卷和接替卷；
- 订单周期；
- 异常明细及建议；
- 最终卷状态。

### 14.4 冷备卷详情

展示当前卷资料、封存快照、订单周期、内容统计、完整性结果、准备离线/确认挂载记录、操作审计，以及该卷关联订单的查询入口。

### 14.5 操作按钮规则

- `HOT/ACTIVE`：显示“转冷备”，必须选择接替卷。
- 普通 `HOT/READ_ONLY`：已有其他健康 ACTIVE 时显示“转冷备”，不重复选择接替卷。
- `HOT/READ_ONLY + REPAIR_REQUIRED`：显示“重新封存”“放弃尝试”和失败报告；重新封存创建新 attempt。
- `COLD/ONLINE/READ_ONLY`：显示“准备离线”。
- `COLD/OFFLINE/READ_ONLY`：显示“确认挂载”。
- `COLD/UNAVAILABLE/READ_ONLY`：显示“重新探测/确认挂载”，并展示异常。
- `HOT/UNAVAILABLE/ACTIVE`：显示“确认活动卷挂载”和“故障切换”；故障切换必须选择健康 STANDBY 并二次确认。
- `HOT/UNAVAILABLE/READ_ONLY`：显示“确认历史热备卷挂载”；成功后只恢复为 HOT/ONLINE/READ_ONLY。
- 有阻塞任务时按钮可点击以查看阻塞原因，但提交必须被后端拒绝，不能只依赖前端禁用。

## 15. 审计、日志与错误信息

下列操作必须记录操作人、时间、请求 ID、源状态、目标状态、源卷、接替卷、结果和失败原因：

- 首卷自动激活；
- 活动卷切换；
- 发起整盘转冷备；
- 封存检查成功或失败；
- 冷备最终提交；
- 准备离线；
- 确认挂载；
- 身份校验失败；
- 冷备文件读取或摘要校验失败。

错误信息必须面向管理员可处理，至少包含卷名称、卷 ID、任务编号或订单号、文件相对路径和建议动作。不得只返回“状态冲突”或“操作失败”。绝对路径是否展示应遵循管理员权限和日志脱敏策略。

## 16. 旧冷备功能处置

### 16.1 本期退出主流程

以下旧能力不再作为整盘冷备入口：

- 冷备磁盘独立登记 `bk_cold_disk`；
- 创建 `bk_cold_batch`；
- `COLD_WRITE` 将部分订单包复制到另一卷；
- 冷备批次“校验”状态按钮；
- `HOT_CLEANUP` 删除热备副本；
- `COLD_IMPORT` 和导入区 ZIP 扫描；
- 前端要求管理员输入任意 `coldRoot`。

### 16.2 兼容原则

- 已存在的旧批次和任务记录必须保留只读查询与审计能力，不因新方案上线而删除。
- 新版本不得再从主界面创建上述旧任务。
- 旧表是否迁移、归档或后续删除由实施计划根据现存生产数据决定，需求阶段不允许直接破坏性删除。
- 新整盘冷备不写 `cold_covered_at`、`hot_deleted_at` 或虚构第二份冷备副本。
- 制品当前属于 HOT 还是 COLD，应由其所属卷当前 `tier` 派生，不再依赖 `COLD_BATCH` 位置类型表达整盘封存。

### 16.3 上线切断规则

新版本部署前必须执行升级前检查，确保不存在状态为创建中、运行中、取消处理中或可重试的 `COLD_WRITE`、`HOT_CLEANUP`、`COLD_IMPORT` 旧任务。发现未终结旧任务时阻止升级或要求管理员先让其终结，不能在新旧语义之间自动迁移任务。

新版本上线后：

- 服务端旧创建、重试和热备清理接口返回明确的“功能已停用”业务错误，不得只隐藏前端入口；
- 调度器不再认领新的旧类型任务；若绕过升级检查遗留非终态旧任务，必须标记为“不支持的旧任务，需人工处理”，绝不能继续执行 `HOT_CLEANUP` 删除文件；
- 已成功、失败或取消的历史任务和批次只读保留；
- 新查询仍能展示旧 `COLD_BATCH` 副本，但不得把它与新整盘封存记录合并成同一事实；路由时统一依据副本台账和所属卷的当前可读性；
- 数据迁移和回滚脚本必须先禁用旧删除能力，再开放新封存入口。

旧 `COLD_BATCH` 只有在上线迁移中成功回填到明确的 `bk_storage_volume` 和副本位置台账后，才允许继续作为可读历史副本。无法证明物理卷身份或无法映射路径的旧记录必须标为“旧冷备位置不可用”，仅保留查询和审计，不能参与下载或恢复路由。迁移报告必须列出成功映射、待人工处理和不可映射数量。

## 17. 异常与边界场景

1. **只有一块卷**：不得转冷备，提示先纳管并选择接替卷。
2. **接替卷容量不足或不可写**：拒绝，不改变任何卷状态。
3. **存在运行中任务**：拒绝，不排队，不自动继续。
4. **切换后完整性失败**：接替卷保持 ACTIVE，原卷保持 HOT/READ_ONLY。
5. **封存检查进程崩溃**：任务恢复或明确失败，不能自动把原卷设为 COLD。
6. **封存最终提交并发冲突**：拒绝提交并重新核对，不覆盖其他状态变化。
7. **准备离线时存在下载**：拒绝并显示读取引用。
8. **盘未拔出但已准备离线**：系统按 OFFLINE 处理，不再路由读取。
9. **冷盘重新插入但盘符变化**：通过卷标记匹配原卷，确认后更新当前路径信息。
10. **相同盘符插入其他盘**：身份不匹配，禁止确认挂载。
11. **卷标记缺失或损坏**：保持 OFFLINE/UNAVAILABLE，不自动重建标记。
12. **重新挂载后单个文件损坏**：拒绝该订单下载/恢复，标记副本异常并告警。
13. **订单存在其他在线副本**：优先使用健康在线副本，不强制插入冷盘。
14. **订单创建时间缺失**：封存检查失败并列出订单，不能生成不可信周期。
15. **数据库有记录但文件缺失，或磁盘有未登记文件**：受管记录缺失文件必须失败；受控业务命名空间内未登记文件必须作为孤立文件阻断封存，明确排除的系统文件除外。
16. **首次纳管并发**：只能有一个首卷成为 ACTIVE，其余健康卷进入 STANDBY。
17. **活动卷硬件突然离线**：进入故障降级状态，停止新备份并告警，不把未知卷自动提升为 ACTIVE，除非已有独立自动切换策略明确授权。
18. **封存任务取消**：当前文件安全点结束，接替卷保持 ACTIVE，源卷进入 HOT/READ_ONLY + REPAIR_REQUIRED；不回切。
19. **封存期间接替卷请求切换或停用**：因生命周期操作保留而拒绝，但正常订单备份仍可写入接替卷。
20. **准备离线后未拔盘**：健康调度器不得自动改回 ONLINE；管理员可通过确认挂载撤销离线准备。
21. **读取中途意外拔盘**：当前下载/恢复失败并释放租约，卷标记为 UNAVAILABLE，其他台账不删除。
22. **同一卷同时出现在多个路径**：视为重复挂载或标记复制冲突，全部拒绝确认挂载。

## 18. 权限与安全要求

- 只有管理员可纳管卷、转冷备、准备离线和确认挂载。
- 普通查询权限可以看到业务需要的卷名称和在线状态；物理路径、指纹和详细存放位置按权限控制。
- 所有相对路径必须防止目录穿越、符号链接越界和根目录逃逸。
- 卷标记不能由浏览器提交内容覆盖。
- 不能根据管理员输入的任意绝对路径执行封存或读取。
- 转冷备、准备离线和确认挂载接口必须幂等或能识别重复请求，避免双击产生重复任务或状态破坏。

## 19. 验收标准

### 19.1 首次纳管

1. 空数据库首次纳管健康卷 A 后，A 自动成为 `HOT/ONLINE/ACTIVE`。
2. 已有 A 为 ACTIVE 时纳管 B，B 不抢占 A，默认成为 `HOT/ONLINE/STANDBY`。
3. 并发纳管 A、B 时最终只有一块 ACTIVE。
4. ACTIVE 卷意外不可用后可通过身份复核恢复 ONLINE；也可由管理员选择健康 STANDBY 执行原子故障切换，切换失败时整体回滚。
5. 故障切换后原卷重新接入，只能经管理员确认恢复为 HOT/ONLINE/READ_ONLY，不会自动恢复 ACTIVE。

### 19.2 成功转冷备

1. A 为 `HOT/ACTIVE` 且包含多个日期订单，B 为健康 `HOT/STANDBY`。
2. 管理员选择 B、填写备注并提交。
3. 系统原子切换为 B `HOT/ACTIVE`、A `HOT/READ_ONLY`。
4. 新备份只写 B。
5. 系统全量校验 A 上所有受管文件。
6. 校验通过后 A 成为 `COLD/ONLINE/READ_ONLY`。
7. A 的订单包卷 ID 和相对路径保持不变。
8. 封存快照中的订单周期等于盘内订单 `order_created_at` 的最小值和最大值。
9. 全过程任意时刻不存在两个 ACTIVE。
10. A 进入 SEALING 后不能再创建来自 A 的下载或恢复租约，B 在校验期间仍可接收新备份但不能被切换或停用。

### 19.3 转换阻塞与失败

1. 只有 A 一块卷时转冷备被拒绝。
2. A 或 B 存在运行中相关任务时被拒绝，任务结束后不会自动转换。
3. A 上任一文件缺失、大小不符、SHA 不符或 ZIP 损坏时，封存失败。
4. 失败后 B 保持 ACTIVE，A 保持 HOT/READ_ONLY，并能查看完整失败报告。
5. 修复后必须由管理员重新提交，系统重新全量检查。
6. 重新提交时 A 已为 HOT/READ_ONLY，不重复执行 A→B 切换，生成新的 attempt 并保留旧失败报告。
7. 校验进程失联后只能由新 runner 在旧 lease 过期后接管同一 attempt，已完成条目不重复提交，处理中条目从头校验。
8. 管理员取消封存后 B 保持 ACTIVE，A 保持 HOT/READ_ONLY + REPAIR_REQUIRED。

### 19.4 离线与检索

1. A 为冷备在线且存在下载/恢复读取时，“准备离线”被拒绝。
2. 无读取任务时准备离线成功，A 成为 `COLD/OFFLINE/READ_ONLY`。
3. A 离线后仍能按订单号查到订单、卷名称、查找备注、存放位置和周期。
4. 只有 A 离线副本的订单不能下载或创建线上恢复任务，并显示明确插盘提示。

### 19.5 重新挂载与直接使用

1. A 以相同或不同盘符重新插入时，不自动在线。
2. 管理员确认挂载后通过卷 UUID 正确识别 A，更新为 `COLD/ONLINE/READ_ONLY`。
3. 插入其他物理盘占用原盘符时确认失败。
4. 无需复制回 B，即可直接下载 A 上订单包。
5. 无需复制回 B，即可从 A 创建并完成线上恢复。
6. 下载或恢复期间不能准备离线 A。
7. 读取前摘要校验失败时拒绝操作并产生文件级告警。
8. 确认挂载时发现同一卷 UUID 出现在两个路径，两个候选均不能上线。
9. 准备离线与新下载并发时只能有一个成功：取得租约则离线失败，先进入 GOING_OFFLINE 则下载失败。
10. 下载客户端中断、恢复任务取消或服务崩溃后，读取租约按协议释放或安全过期，不永久阻塞离线。
11. 线上恢复取源与准备离线并发时遵循与下载相同的原子租约规则，不能出现任务已绑定离线卷却没有租约的状态。

### 19.6 状态展示一致性

1. A 从 HOT 变为 COLD 后，订单和文件页面立即显示当前卷为 COLD，无需批量改写订单表。
2. 历史备份任务保留执行时写入 HOT 的事实，同时展示卷当前为 COLD/OFFLINE 或 ONLINE。
3. 任务详情、订单详情、文件详情和存储卷详情中的卷 ID、名称、相对路径和当前状态一致。
4. 旧冷备记录只有在完成卷与副本位置映射后才能显示为可读取；无法映射的记录明确显示“旧冷备位置不可用”。

- 使用两个独立本地盘或目录模拟 A、B，完成备份、切换、封存、离线、重新挂载、下载和线上恢复闭环；

- 验证大文件和大量订单时封存任务进度、超时和恢复能力。
- 验证封存期间接替卷继续写入但不能执行生命周期切换；

### 20.4 回归测试

- 正常订单备份始终写入唯一 HOT/ACTIVE；
- 热备卷切换后历史订单仍可下载和恢复；

- 存储容量监控、空间预留、订单文件展示和任务详情不因新状态机回归。

## 21. 实施阶段必须解决的现有差距

后续实施计划至少应覆盖：

1. 修改首次纳管逻辑，自动建立第一个 `HOT/ACTIVE`。
2. 将当前普通 `to-cold` 状态更新替换为带接替卷、备注和封存检查的受控流程。
3. 允许承载活动文件位置记录的 HOT 卷整体转为 COLD；活动副本是封存对象，不再是禁止转换的理由。
4. 增加卷封存记录、检查明细、内容统计和查询接口。
5. 增加持久化读取引用或租约，使同步下载也能阻止离线。
6. 完善任务与源卷/目标卷引用判定，覆盖取消处理中和失败重试状态。
7. 完善订单包与补传文件的卷路由，确保 COLD/ONLINE 可直接读取。
8. 完善订单、文件、任务和卷页面的实时状态关联展示。
9. 增加准备离线和手动确认挂载流程。
10. 从主界面和新任务入口退出旧冷备批次写出、热备清理和导入区流程。
11. 制定旧冷备数据只读兼容和数据库迁移方案。
12. 修订原存储卷设计文档中与本需求冲突的第 6 节及相关验收场景，明确本文为最新冷备语义。

## 22. 后续独立需求

主流程实现并通过全部验收后，再单独讨论“临时导入区”冗余方案。该方案需要重新设计复制后的卷归属、相对路径重建、数据库台账迁移、幂等导入、重复订单、空间预留和原冷盘/新热备卷之间的副本关系，不得复用当前未经统一的旧导入实现直接上线。
