# 文件关系不完整时自动降级备份设计

## 1. 背景与目标

严格订单备份在生成线上 Manifest 时，只要任一有效业务关系无法形成可靠文件资产，就返回不可重试的 `RELATION_BROKEN`。现有系统会将该订单直接置为失败，管理员只能在任务明细中逐单创建独立 `DEGRADED_BACKUP` 任务。大量历史脏关系会因此长期阻塞订单业务快照和其余可用文件的备份。

本设计在保留严格完整性语义的前提下，为新备份任务增加可配置的自动降级补偿：严格备份失败后，只对 `RELATION_BROKEN` 订单在同一任务内执行显式降级 Manifest，形成 `REAL + INCOMPLETE` 的终态备份。即使没有任何可恢复文件，也保存订单业务快照和关系缺口。

## 2. 已确认的产品决策

- 配置默认开启。
- 自动降级发生在原备份任务的补偿阶段，不创建独立子任务。
- 自动降级允许零文件结果；只要订单业务快照、关系缺口和终态凭证完整，就视为不完整备份成功。
- 配置只影响启用后新创建的任务；历史失败任务不自动扫描或补偿。
- 所有完整或不完整备份都成功时，任务终态为成功；仍有订单未形成任何备份时，任务为部分失败或失败。
- 不完整备份永久明确标记“文件可能不完整”。

## 3. 配置模型

新增全局布尔配置：

| 属性 | 值 |
|---|---|
| 配置键 | `backup.auto-degrade-on-relation-broken` |
| 页面名称 | 文件关系不完整时自动降级备份 |
| 分类 | `BACKUP_COLLECTION` / 备份采集策略 |
| 默认值 | `true` |
| 类型 | `BOOLEAN` |
| 说明 | 严格备份因 `RELATION_BROKEN` 失败后，在同一任务补偿阶段自动执行不完整备份；即使没有可恢复文件也保存订单快照和关系缺口。 |

配置进入允许修改键集合并按严格布尔值校验。自动任务和管理员立即扫描创建任务时，把该值固化进 `bk_job.config_snapshot_json`；执行器只读取任务快照，不读取中途变化的全局配置。已有任务保持创建时行为。

手工指定订单创建的普通严格备份任务也遵循其创建时配置快照。显式人工 `DEGRADED_BACKUP` 任务保持现状，不再套用自动降级策略。

## 4. 执行流程

### 4.1 首轮严格备份

1. `ORDER_BACKUP` 或 `MANUAL_BACKUP` 任务按现有严格 Manifest 逐单执行。
2. 可重试的网络、下载、对象存储和本地存储异常进入现有普通重试队列。
3. `RemoteCallException(code=RELATION_BROKEN, retryable=false)` 不进入普通重试队列：
   - 配置关闭时，保持终态失败；
   - 配置开启时，记录原始失败证据并加入自动降级补偿队列，订单状态使用独立的非终态，例如 `DEGRADE_PENDING`，不得提前显示为最终失败。
4. 其他不可重试业务异常仍直接终态失败，禁止自动降级。

### 4.2 普通重试阶段

先完成现有普通失败重试，避免临时故障与数据完整性补偿混在一起。普通重试仍只执行严格 Manifest，绝不因为网络错误自动切换为降级模式。

如果普通重试最终返回 `RELATION_BROKEN`，且任务快照开启自动降级，也加入自动降级补偿队列。

### 4.3 自动降级补偿阶段

1. 任务进入可观察步骤 `AUTO_DEGRADED_BACKUP`，日志记录待补偿订单数、触发错误和配置快照。
2. 对队列中每个订单调用显式降级 Manifest 接口。
3. 线上新增稳定业务码 `RELATION_GAPS_RESOLVED`（HTTP 409、不可重试），表示降级解析时已经没有任何关系缺口。不得继续复用宽泛的 `STATE_CONFLICT` 或匹配错误文本。本地收到该业务码后重新执行严格 Manifest，优先形成 `COMPLETE` 备份。
4. 降级 Manifest 可包含零个资产，但必须包含订单业务快照、`backupCompleteness=INCOMPLETE`、至少一条关系缺口及其摘要。
5. 可用文件继续执行现有下载、打包、暂存、回执和发布流程；零文件也生成包含订单快照、Manifest 和关系缺口的有效订单包。
6. 自动降级阶段遇到可重试异常时沿用 `backup.retry.max-retries` 和 `backup.retry.delays-seconds`；不可重试异常或重试耗尽才成为终态失败。
7. 暂存和回执幂等键必须区分同一订单的严格尝试与自动降级尝试，同时继续服从“每个订单只能形成一个有效终态凭证”的线上约束。

### 4.4 有界切换状态机

严格与降级模式之间禁止无限往返：

1. 首次严格解析得到 `RELATION_BROKEN` 后进入自动降级。
2. 降级解析成功返回缺口时，直接完成不完整备份。
3. 降级解析返回 `RELATION_GAPS_RESOLVED` 时，只允许进入一次“关系已修复严格确认”分支。
4. 该严格确认成功时形成完整备份；发生可重试基础设施异常时，在订单剩余重试预算内继续严格确认。
5. 该严格确认再次返回 `RELATION_BROKEN` 时，只允许最后再读取一次降级 Manifest；若得到缺口则完成不完整备份，若再次返回 `RELATION_GAPS_RESOLVED` 则以本地稳定错误 `RELATION_STATE_UNSTABLE` 终止，禁止继续切换。
6. 该严格确认出现其他不可重试错误或耗尽重试预算时终态失败。

每个订单的重试预算跨普通重试和自动降级阶段统一计数，不能因切换模式重新获得一套无限重试次数。

### 4.5 崩溃恢复、取消与并发

- `DEGRADE_PENDING`、`DEGRADING` 必须持久化在 `bk_job_order.status`，补偿队列可以从任务订单证据重建，不能只保存在执行器内存中。
- 同一任务因租约过期或进程重启恢复时，跳过已有有效终态快照的成功订单，恢复 `DEGRADE_PENDING/DEGRADING` 订单；若存在 `STAGED/RECEIPT_ACCEPTED` 制品，优先使用现有断点恢复流程。
- 自动降级等待、逐单开始、文件下载、回执和发布阶段继续执行任务取消安全点。取消后不在后台继续补偿；管理员重试任务时创建新任务，并重新固化当时配置。
- 严格和降级尝试使用包含模式的幂等键，例如 `...:mode:COMPLETE` 与 `...:mode:INCOMPLETE`。
- 若并发任务已赢得线上终态凭证，当前暂存制品标记 `SUPERSEDED`。本地存在对应 `AVAILABLE` 快照时，将当前订单对账为已覆盖并读取其权威完整性；不存在可验证本地快照时保持失败，不能仅凭远端冲突伪造本地备份成功。

## 5. 状态、统计与证据

### 5.1 订单结果

- 完整成功：`status=SUCCEEDED`，快照 `backupCompleteness=COMPLETE`。
- 自动降级成功：`status=SUCCEEDED`，快照 `backupCompleteness=INCOMPLETE`。
- 自动降级等待/执行：使用 `DEGRADE_PENDING` / `DEGRADING` 等非终态展示语义。
- 未形成任何终态快照：`status=FAILED`，保留最后一次异常和最初 `RELATION_BROKEN` 触发证据。

`bk_job_order` 继续保存任务内执行状态；权威完整性来自发布后的 `bk_order_snapshot.backup_completeness`。任务订单查询应批量投影：

- `backupCompleteness`；
- `relationGapCount`；
- 自动降级来源标记，例如 `autoDegraded=true`（读取投影或任务证据，不伪造成任务失败）。

### 5.2 任务汇总

任务 `result_json` 增加：

- `completeSucceeded`：完整备份成功订单数；
- `incompleteSucceeded`：不完整备份成功订单数；
- `orderFailed`：未形成任何备份的订单数；
- `autoDegradedAttempted`：自动降级尝试数；
- `autoDegradedSucceeded`：自动降级成功数。

`orderSucceeded = completeSucceeded + incompleteSucceeded`，保持现有总数兼容。

计数统一按订单去重：`autoDegradedAttempted` 表示进入自动降级补偿队列的唯一订单数，不是 HTTP 调用或重试次数。进入补偿后因关系已修复而最终形成完整备份的订单仍计入 attempted，但不计入 `autoDegradedSucceeded`；它只计入 `completeSucceeded`。重试次数继续只写执行日志和已有尝试字段。

任务终态：

- `orderFailed=0`：`SUCCEEDED`，即使存在不完整备份；
- `0 < orderFailed < orderTotal`：`PARTIAL_FAILED`；
- `orderFailed=orderTotal`：`FAILED`。

## 6. 前端展示

### 6.1 系统配置

配置由现有通用系统配置页展示为“启用/停用”，无需新增专用页面或自定义控件。说明必须明确：仅处理 `RELATION_BROKEN`，会生成永久标记的不完整备份，并允许零文件订单完成。

本期前端范围仅为 `yigongbao-backup-web` PC 管理端。H5 和主医工宝业务前端不新增配置或任务管理页面。

### 6.2 任务详情

- 任务汇总分别展示“完整备份 / 不完整备份 / 失败”。
- 订单行最终状态仍为成功，但增加橙色 `文件可能不完整` 标签、缺失关系数量和“自动降级”来源。
- 订单抽屉展示缺口原因摘要；已有快照详情继续作为完整关系缺口证据入口。
- 补偿中显示“等待自动降级”或“正在自动降级”，不能提前显示红色失败。
- 自动降级失败、配置关闭或不符合触发条件时，继续显示管理员手动“降级备份”入口。

订单文件页和恢复页沿用现有 `INCOMPLETE` 提示。恢复只上传包中真实存在的资产；零文件不伪造上传目标。

## 7. 日志与审计

任务日志至少记录：

- 自动降级策略是否启用及其任务快照值；
- 严格失败进入补偿队列；
- 自动降级阶段开始、每单尝试、重试、成功或失败；
- 降级前关系已修复并回到严格备份；
- 最终完整/不完整/失败数量。

日志和结果必须保留原始 `RELATION_BROKEN` 的 requestId、原因码和首条缺口原因。配置修改继续走现有配置版本与管理员审计机制。

## 8. 安全边界与非目标

- 只允许稳定业务码 `RELATION_BROKEN` 触发，禁止基于错误文本模糊匹配。
- 数据库、认证、权限、预签名、网络和存储异常不能伪装为关系缺口。
- 自动降级不修复线上脏关系，不恢复已删除文件，也不把不完整备份标记为完整。
- 不自动补偿历史失败任务。
- 不移除手动降级能力。
- 不改变候选口径：成功的不完整凭证与完整凭证一样使订单退出后续普通备份候选。
- 不改变恢复原子性：实际存在的全部资产成功恢复后才提交；零资产降级快照按现有降级协议提交业务快照和缺口事实。

## 9. 兼容与迁移

- 新配置通过初始化基线和独立增量迁移 `INSERT ... WHERE NOT EXISTS` 加入，不覆盖现场值。
- 不要求新增核心业务表字段；任务订单完整性优先通过现有快照表批量投影。若实现评估证明仅靠投影无法稳定区分补偿来源，可增加明确且可回填的执行来源字段，但不得复制权威完整性状态。
- 旧任务缺少配置快照字段时按 `false` 处理，保证部署后不会改变正在执行或已创建任务的行为；只有新任务按默认数据库配置 `true` 固化。
- 现有独立 `DEGRADED_BACKUP` 历史任务和接口保持兼容。

## 10. 验收标准

1. 默认配置为开启，系统配置页可修改且版本化保存。
2. 新任务固化配置；修改全局配置不改变已创建任务。
3. `RELATION_BROKEN` 订单在同一任务内自动形成 `INCOMPLETE` 快照。
4. 零资产降级 Manifest 仍能成功打包、提交和发布。
5. 其他错误永不触发自动降级。
6. 自动降级临时失败遵循现有订单重试策略，最终失败保留手动入口。
7. 关系在补偿前修复时，形成 `COMPLETE` 而非不必要的 `INCOMPLETE` 快照。
8. 关系在严格和降级解析间反复变化时，状态机有界终止，不产生无限循环或重复终态凭证。
9. 执行器重启可以从持久化订单状态和暂存制品恢复自动降级补偿，取消后不继续后台执行。
10. 并发终态冲突只在存在可验证本地快照时对账为已覆盖，否则保持失败。
11. 全部订单形成完整或不完整快照时任务为 `SUCCEEDED`；仍有失败时正确形成 `PARTIAL_FAILED/FAILED`。
12. 首页、任务详情、订单列表和订单详情持续清晰展示“文件可能不完整”。
13. 历史任务不会被自动补偿，现有显式降级和恢复流程无回归。
